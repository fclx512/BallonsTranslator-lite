# 手动释放内存（卸载模型 → 交回工作集）

> 状态：已完结归档（2026-09-20 删除 `cudaDeviceReset` 支路后定稿）——本篇为压缩存档，只留结论与指针；实施过程见 git 历史。

**入口**：设置页 Models → Management 的「释放内存」按钮，**用户手动点、点前弹确认**。
**分层**：逻辑在 `utils/memory_release.py`（无 Qt、可注入替身），提示与忙闲判据在 `ui/mainwindow.py::MainWindow`。

## 实测数字（2026-09-17，本机 RTX + torch 2.13+cu132）

ppocrv6 检测 + paddleocr_v6 OCR **各跑一次**（都 `device=cuda`），读数＝进程工作集（`GetProcessMemoryInfo`，即任务管理器看到的"内存"）：

| 步骤 | 工作集 |
|---|---|
| 引擎导入 + 开项目（未用 CUDA） | 590 MB |
| 跑完一轮 CUDA | 1503 MB |
| 卸载全部模型 + `gc` | 1503 MB（现有「卸载全部模型」按钮几乎没用，只掉 0~75MB） |
| `torch.cuda.empty_cache()` + `ipc_collect` | 1503 MB（也没用，占的不是 torch 池） |
| `psapi!EmptyWorkingSet()` | **111 MB**——大头在这一步 |
| 之后再用一次 CUDA（ORT 会话） | 420 MB（首次 0.33s、第二次 0.01s） |

两条被推翻的旧判断（原写在 `docs/技术实现/区域再检测_设计与实现_存档.md` 的内存一节）：① **不是**"拉起了一个 CUDA 进程"——CUDA 上下文与 ORT 会话都在本进程内，工作集还含驱动侧 DLL（模块工作集合计 350 → 407MB，`cublasLt64_13.dll` 单项就 144MB）；② **不是**"只能关进程退还"——进程内靠 `EmptyWorkingSet` 即可 1503 → 111MB，要"确定性真释放到进程外"才需要子进程（本机重建代价 ≈2~3s：引擎导入 1.8s + 首个 CUDA 会话 0.3~0.8s）。

## 两步的分工与语义（别混）

| 步骤 | 函数 | 效果 | 语义 |
|---|---|---|---|
| 卸载模型 | 调用方给的 `unload` 回调（`ui/module_manager.py` 的 `unload_all_models`） | 0~75MB | 真卸载，但**几乎不还内存**；价值是让 trim 时少留脏私有页（GPU 侧也顺带空出来） |
| 交回工作集 | `utils/memory_release.py::return_working_set` | −1000MB 量级 | **交回，不是 free**：页退回系统备用内存，私有脏页进 pagefile，页表映射还在、**下次访问要 fault in** |

对外文案一律按上表写：本按钮的效果是**交回**，不写"真释放内存"——混为一谈会被当成假释放。

## 安全铁律（都有实测依据）

1. **不能有 CUDA／推理在跑**：管线、四个"切换模块"线程、区域再检测的后台检测线程（其检测器可配成 CUDA）。忙闲判据命中时 `ui/mainwindow.py::MainWindow` **直接拒绝**并提示等待。
2. **先卸载再交回**：卸载回调抛异常或返回 `False` 时照常走 trim（两步互不依赖），但结果提示换成 warning 文案——读数不好看时用户得知道为什么。
3. **不自动触发**：交回工作集会把界面也要用的页换出去，紧接着的交互可能卡一下（毫秒级），所以是手动按钮，不做"跑完自动"。

## 为什么不做「销毁 CUDA 上下文」（2026-09-20 实测后删除）

按钮此前还有第二支 `cudart!cudaDeviceReset()`。用户报「点了释放内存之后 `paddleocr_vl_manga` 再也跑不起来」后复现，结论是**这个能力不能要**：

| 现象 | 实测 |
|---|---|
| `torch.cuda.is_available()` / `is_initialized()` | **仍返回 `True`** ⇒ 常规判据全部失效 |
| 第一次真实分配（`torch.zeros(4, device='cuda')`） | `Torch.AcceleratorError: CUDA error: invalid argument`（`cudaErrorInvalidValue`） |
| 同一段代码另一次 | **进程直接段错误**，exit `0xC0000005`（整个应用没了） |
| 进程内恢复 | `torch.cuda.init()` / `set_device` / `empty_cache` / `synchronize` / `_cuda_clearCublasWorkspaces()` / 直调 `cudart` 全试过——**没用**，失败点就是第一次分配本身 |
| 加载 torch 模型 | `AutoModelForCausalLM.from_pretrained(...).to('cuda')` 在 `.to()` 里就炸 |

真还的量级只有 **−71 ~ −166MB**，代价是本次会话的 GPU 模型全部不可用、必须重启应用，还可能把进程打崩。整条路径（含配套的进程级标记与模块侧拦截）已删除，由 `tests/test_memory_release.py::RemovedCapabilityTest` 钉住"别加回来"。真机复算与全部读数：`scripts/probes/release_cuda_context_aftermath.py`。

> 真要"确定性释放到进程外"（连驱动侧显存也归零），唯一干净的做法是把这段工作放进子进程、然后结束子进程——重建 ≈2~3s。这需要把管线阶段搬出 GUI 进程，收益不抵架构改动。

## 另外不做的事

① 不自动在每次跑完管线时释放；② 不做子进程隔离（理由见上）；③ 不新增第二套清缓存语义——`modules/base.py` 里的 `soft_empty_cache` 仍是管线侧的日常清理（只管 torch 池、不动工作集），本按钮只是"用户按需要回内存"。

## 验收

- `tests/test_memory_release.py`：步骤顺序、读数记录、单步异常不外抛、trim 可关、`RemovedCapabilityTest` 钉住"销毁 CUDA 上下文"不再存在（全用替身，不碰真 CUDA）。
- 真机复核 `scripts/probes/release_cuda_context_aftermath.py`：期望**释放后 torch 分配/matmul 照常、`paddleocr_vl_manga` 加载（约 4s）与识别照常**；末尾那段"若销毁上下文会怎样"只作历史证据（可能段错误，故放最后）。
- GUI 侧人工确认两件事：忙闲判据真的挡住了管线运行中的点击；**释放之后下一次跑管线照常**（模型重新加载、结果与释放前一致）。
