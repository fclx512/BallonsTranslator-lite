# 泛用工作台 · 规划

> 状态：**定稿**。本文记录定位与决策、核实过的现状事实、量化依据、实现层调研结论（§9），以及**已关闭议题的结论留档（§8）**。**除 §6.5／§6.6（明确延后）外无未决项。**
> 上游文档：[AI辅助功能_规划](AI辅助功能_规划.md)（标签体系与框级动作）、[术语剧情工作台_交接](术语剧情工作台_交接.md)（现有工作台的数据流与线程模型）。

## 1. 起因

用户实机使用后提出：现有 agent 工作台（`ui/glossary_agent_panel.py::GlossaryAgentPanel`）只服务术语与剧情两件事，与标签体系割裂；希望改组为"泛用工作台"，能快速处理各管线阶段冒出的问题（举例：清理置信度低且没识别出内容、或只有纯数字的框），以此把各模块联通起来。

## 2. 定位（已定，2026-09-14）

用户澄清后的定义，取代"泛用 = 什么都能聊"的误读：

1. **不做通用 chat 对话。** 沿用 [AI辅助功能_规划](AI辅助功能_规划.md) §2 的结论：对话形态必然过度承诺，能力边界必须由形态自证。
2. **"泛用"的准确含义** = 工程化处理出**确定性数据** → 人用打标或其他交互方式**灵活给 AI 提供信息** → 走**收敛的出口**。既避免纯程序化的僵化死板，也避免 agent 模式过分自由导致结果不可控。
3. **不引入重型提示词。** 项目代码不做 agent 能力设计，也不需要那套资源消耗。
4. **交互设计的本质是人机接口。** 标签以及将来其他交互形态，都是"方便人与 AI 交互的工具"；情况复杂时预留人工输入提示词介入的通道。
5. **总原则：** 除开明确可以完全放心交由代码处理的事务，都应由用户审查确认，不擅自修改。

## 3. 工作台 = 任务容器

工作台从"术语专用面板"重新定位为**任务容器**：术语提取、剧情摘要、问题清理是同一个容器承载的多种**任务类型**，各走同一套三段结构。

| 任务类型 | 状态 | 确定性数据来源 | 出口 |
|---|---|---|---|
| 术语提取 | 已实现 | 只读工具 + 人工补充 | 草稿表 → 落盘 json |
| 剧情摘要 | 已实现 | 只读工具 + 分页汇总 | 草稿表 → 落项目字段 |
| 问题清理（**任务族**） | **待建** | 程序筛选器（见 §6） | 各子任务出口不同：误识别清理 → 驳回标记／一键批量删除已确认；批量合并 → 合并建议；批量框扩张 → 扩张；批量简单背景修复 → 纯色覆盖。**所有批量出口均弹窗告知后果（D27）** |

**任务导航的取值与默认顺序**：导航列表按"任务"排列，**默认顺序＝ §4 用户工作流顺序**：① 误识别清理（§7 四类）→ ② 批量合并相邻框 → ③ 批量框扩张 → ④ 批量简单背景修复 → ⑤ 术语提取 → ⑥ 剧情摘要。前四项属"问题清理"任务族，**只有它们参与跳步提示的"还有 N 个未处理"计数**；术语／剧情是探索性任务、无"未处理标记"概念，不计入计数。运行时不门禁、可任意跳转（D37）；跳步提示即以该顺序为依据（D16 的"清理 → 合并"是该顺序的子集）。同一容器内各任务共用三段结构（D20）。

**结构性观察**：把用户完整工作流（§4）过一遍，AI 真正非它不可的只有两处——手写字猜测、词不达意的重译（将来加译文伸缩）；其余全部是"程序筛选 → 人看一眼 → 确认/驳回"。因此工作台的定位应比"AI 交互入口"更冷一档：**问题队列 + 人机确认台**。

架构含义：**每个任务类型要能声明"这条需不需要 AI"**。不需要 AI 的条目（误框、简单背景、溢出检测）就是"看一眼 → 确认/驳回"，只有需要 AI 的条目才走确认卡。

## 4. 用户工作流与痛点地图

| 步骤 | 用户做法 | 痛点 / 优化机会 |
|---|---|---|
| 概览 + 选默认样式 | 概览全文，选原文最常用字体样式作项目默认样式 | 无（自述这步是为省后续功夫）；可选 vision 辅助样式推荐，低优先 |
| 检测 + OCR | 跑管线 | — |
| 逐页人工审校 OCR | 误识别删除；手写字用各种方式补全；错误分隔的文本合并 | 用户惯用检测模型**一行一框**（竖排则一列一框），**合并量极大** → 对应措施：批量合并相邻框（§6.3）；此外需要给渲染留出空间 → 批量框扩张（§6.4） |
| 清理原图嵌字 | 因修复管线不可控，**基本纯手动** | 希望**只对"简单背景"一键纯色覆盖**，复杂背景保留手动；**不处理脏页**（有手动重渲 + 逐页审查时自然消化） |
| 术语表 + 剧情概览 | 导出原文文档 → **外部 agent** 生成 → 一到两轮人工补充纠正 | 项目内功能还不够好；用户明确功能完善后会转回项目内。另：翻译功能项**太多太杂，难以判断用哪个** |
| 审查译文 + 调样式 | 逐页审查译文、按原文样式精细调字号间距 | 最费力：修词不达意的译文、微调字号间距。**最折磨：原文/译文文本量差异大 → 气泡填不满/塞不下 → 选字号换行甚至删改译文** |

## 5. 已定决策

| 编号 | 议题 | 结论 |
|---|---|---|
| D1 | 问题载体 | **在标签体系上扩建**。现有 5 个标签只是草案，不代表将来不改动（D38 新增 1 个后为 **6 个**）。 |
| D2 | 误识别类（空文本／纯数字／纯符号／无假名汉字，四类见 §7） | **纯程序化**：仅在 OCR 管线跑完后用正则判断**自动挂标**；**标签工具栏与右键自定义菜单里不提供该标签的人工打标入口**（D38 的"程序专用"声明挡住）。人只去工作台审查是否误杀。**注意与 D32／D33c 的区分**：那里说的"审批现场打误识别标签"是**工作台审批界面内的专用动作**（把该块直接送入误识别清理队列），不是开放标签工具栏的人工打标途径——前者是任务流程的一部分，后者仍被禁止。 |
| D3 | 批量简单背景修复 | 做成**工作台的一个任务**。**批量只覆盖"简单背景"的框，复杂背景仍留给人工手动处理**（用户明确不做自动化）。 |
| D4 | 批量操作的撤销粒度 | **整体一条撤回**。批量操作**一律**走落盘撤销（D21"批量一律落盘"、D35 版本轮转制），不按脏页与否分流——这正是"一条撤回"的落实方式。 |
| D5 | 批量框扩张 | **只扩张渲染区域**（检测模型本身的扩张量对修复已经够用）；除批处理外**还支持单独调整**，交互拟借鉴 PS 的"按住 Alt 拖拽 = 中心缩放"以降学习成本。 |
| D6 | 翻译侧 | 增加一个"自动"功能项可行，但**需备注标示启用后 AI 可能会执行的行为**以提供预期。 |
| D7 | 排序归属 | **手动排序为准**（工具栏已有重排功能：人肉眼判断顺序 + 鼠标划过文本框确认，实测效率可用，是置信度高的识别模型出现前最可靠的方案）。合并重建**不得自动重排**，保留用户既有顺序。 |
| D8 | 合并方案 | 程序打组 → **组级方向判定**（三级：**主判**＝组内 `src_is_vertical` 多数；**交叉验证**＝块顺序一致性，不一致时只在该审批行标注"顺序存疑"，**不改变判定结果、不自动剔除任何组**；**兜底**＝组内无有效 `src_is_vertical` 时改用块顺序，整页都判不出时才用全文统计投票）→ 展示合并建议 → 人工审批 → 一次性应用。 |
| D9 | 问题框分类 | 按 §7 四类实现（空文本／纯数字／纯符号／无假名汉字），程序正则**自动挂标**，人工只审查误杀。 |
| D10 | 批量修复的撤销 | 不在乎形式，只要可用；**优先低内存**，允许牺牲部分体验。 |
| D11 | 审批截图 | **必须 100% 原始比例**（不缩放），否则审查不可信；交互形态须在此约束下设计。 |
| D12 | 容器落点 | **直接在左侧工作台重做**，大幅加宽；画布约占主页面 1/3 或更少；右侧编辑区应可折叠向右收纳（**经 D24 调整为"适度加宽"，折叠收纳暂缓；宽度定稿 460**）。 |
| D13 | 术语/剧情输入 | 篇幅短，**直接把全书原文塞给会话**；保留基本顺序与页面信息；页名须做**格式归一化**（防不规范或超长文件名干扰 AI），AI 输出译文时按映射还原。 |
| D14 | 概览选默认样式 | **不做 vision** 推荐（AI 侧没有可量化数据可依据）。 |
| D15 | 审阅状态的展示 | **仅约束工作台审批界面**（2026-09-16 澄清）：**画布徽标行为完全不变**（`pcfg.show_tag_badge` 不动，不影响既有已上线表现）；工作台内不逐个堆叠程序标签，须有整合／精简显示手段，不让重复信息占满视觉。 |
| D16 | 任务执行顺序 | **合并放在"误识别清理"之后**（＝先审 §7 四类的框，见 §3 的导航顺序）。理由：若先合并，**带问题标签的框**被并进去会使合并后的框也带标且更难定位。 |
| D17 | 标签二分 | **临时标签**（OCR／译文问题）由**程序与用户共同维护消费**；**持久标签**（手写、拟声词）**完全由用户标注**——让 AI 判拟声词本质属于翻译流程，无提示时行为不可控。持久标签可带一个**不参与展示的标记字段**与临时标签区分。 |
| D18 | 撤销的容量策略 | **（2026-09-16 更正）沿用现有步数上限**——`utils/config.py::ProgramConfig` 的 `undo_steps_limit` 即为内存侧的唯一约束，**不新增"撤销占用上限"设置项**。原"动态阈值＋占用上限"方案与 D21 重复且多余：批量操作既已一律落盘，内存侧只剩单框小操作，步数上限已足够；动态阈值还需大动底层，风险收益不成比例。D21 的落盘结论保留——用户自评该结论"稍许激进"（可能过于一刀切），但前提"可接受写盘"成立，暂按此执行、实测后再议。 |
| D19 | Chat tab | **砍掉**。人工提示词入口降级为"消费临时标签时在窗口内提供纠正入口"；批量审批需求待实际体验后再议。 |
| D20 | 工作台组织形态 | **三段式**：① 任务导航（一级）→ ② 候选列表（**逐条可查看**：列表逐行呈现、点选某行即在下方展开其 100% 原比例预览；但**不要求逐条确认**——列表级批量任务支持勾选后一次执行，见 §8 留档第 2 条）→ ③ 执行／写回（无候选时禁用）。**批处理与审批是同一任务的两端，不分家**；需分开的是不同任务类型。 |
| D21 | 撤销实现（细化 D18） | **按操作类型分**，不做动态阈值——动态阈值需大幅动底层、风险大。单框小操作留内存（沿用现有 `QUndoStack`），批量操作一律落盘。 |
| D22 | 一级导航落点 | **复用主窗口左侧已有的 48px 图标栏**（`ui/mainwindowbars.py::LeftBar`），不新建导航控件，以减少改动面；实现后按体验反馈优化。**（D25：单入口。）** |
| D23 | 预览形态 | 选中项在**列表下方展开**（不并排、不弹窗），须 **100% 原比例**（D11）；实现后按实际使用判断是否合适。 |
| D24 | 工作台宽度（回调 D12） | **适度加宽，不走 D12 的激进方案**：以方便查看 100% 原比例审批图为唯一判据（宽度太小则审批效率低）。**定稿：默认维持 `ui/mainwindow.py::MainWindow` 的 `WORKBENCH_WIDTH = 460`**、不预先改动：样本实测合并组图 p90 为 200×208 px，加 D31 外扩（短边 50% ≈ 40 px）后约 280×288 px，在 460 内可 100% 全幅显示、无需滚动；仅 2 个跨栏大组（最大 1827 px）需滚动，而它们本就默认不勾选。右侧编辑区"折叠向右收纳"**暂缓**。实现后若实测不足只改该常量（面板内部宽度自适应，零布局改动）。 |
| D25 | LeftBar 导航形态（细化 D22） | **只设一个"工作台"入口**——改造现有 `glossaryChecker` 槽位（换图标/改名），任务类型切换在面板内部完成；不为每种任务加 LeftBar 图标（§9.1 的互斥手写逻辑零改动）。此类 UI 调整实现后再实际人工评判。 |
| D26 | 队列跳转范围 | 只对条目所在的**页与块**负责（跳转链路见 §9.3）；面板内不做翻页控件——A/D 快捷键可手动逐页切，有其他跳转需求的场景大概率已不再关心工作台内容。 |
| D27 | 误框清理出口 | **提供一键批量删除已确认**：工作台主旨是高效辅助处理纯人工下费时费力的操作，故应有一键操作；**所有批量行为弹窗告知确认后的行为**。删除属新出口，按白名单原则登记，实现含 `proj.pages` 写回 + 撤销命令 + 页代数（§9.7）。**但撤销命令不能复用现成的 `ui/scenetext_manager.py::DeleteBlkItemsCommand`**（它只作用于当前页，见 §6.1），跨页批量须新写。**前期流程（产出译文前）不主动处理脏页**——后续管线迟早推进覆盖，无实际嵌字产出前脏页影响不大（§8 第 2 条）。**"勾选待删除"是会话内界面态、不落盘**——它是"本批次待执行意图"，执行即消失；落盘会留下无法区分"忘了取消"与"确实想删"的残留态。驳回与勾选**两轴正交、互不自动联动**（驳回＝"标签判错、框是正常文本"；勾选＝"框本身该删"），删除执行前的弹窗确认（本条"所有批量行为弹窗告知"）即用户的复核机会。 |
| D28 | 审阅状态机制 | **用 `reviewed` 字段，不改写 `source`**。理由：`source` 表达"标签从哪来"（事实）、`reviewed` 表达"人怎么看"（表态），两者正交；改写来源会让"程序判的标被人驳回"与"人自己挂的标"混为一谈，也与 `utils/block_tags.py::TagDef` 的声明值不一致。`reviewed` 方案只需挂标处（置信度挂标与新增正则挂标）跳过带 `reviewed` 的条目，即可在重跑 OCR 后存活。**驳回可逆、不从队列消失**：语义为布尔（已驳回／未驳回），不引入第三态；驳回后**卡片保留**，只覆盖一层"已驳回"遮罩标识，**再次点击即取消驳回**。驳回的条目不计入"待处理"计数，但仍可见（取消驳回即恢复计数）。**状态模型**：标签条目侧只有 `reviewed` 一个持久表态字段（布尔）；队列的"勾选待删除"是会话内界面态（D27）；**不存在"已确认通过"态——未驳回即待处理**。**驳回粒度＝块级**：一次驳回作用于该块**全部**程序来源标签条目（实现上即对该块所有 program 来源条目置 `reviewed`），与 D38"驳回粒度跟框走"一致；"取消驳回"即清掉这些 `reviewed`。**队列口径**：工作台的"误识别清理"队列＝带 D38 **误识别正则标签**的块（按块去重计）；`ocr_low_conf` **不单独入队**（其出口是 `utils/block_actions.py` 的框级 OCR 校正动作，见 §7 末段），故"**待处理计数 = 队列内块数 − 已驳回块数**"。 |
| D29 | 人工编辑与程序标签 | **人工编辑文本 = 已知晓该框实际情况** → 清除该块全部 program 来源临时标签（`ocr_low_conf` + 误识别类正则标签），**不做自动重判**（编辑后要么已完善、要么会被打上临时标签进消费队列）。注意：标签不进撤销栈，撤销文本编辑不会恢复被清标签（可接受：重跑 OCR 会重算）。人工编辑**不影响**队列的"勾选待删除"状态（两轴正交，见 D27）。**清除口径**：清除＝`utils/block_tags.py::remove_tag` **整条删除**，**不区分该条目是否带 `reviewed`**（人工编辑即知情，无需保留驳回记忆）；清除后该块回到"无标签"状态，重跑 OCR 会重新判定（此时条目已不存在，D28 的 `reviewed` 跳过逻辑自然不适用）。 |
| D30 | 合并与带标框 | 合并规划**排除带未驳回误识别标签的框**，审批界面提示"N 个带未驳回误识别标签的框被排除"；先审完清理再跑合并（D16 的操作顺序由此闭环）。**判据为"未驳回（`reviewed != True`）"**，理由：驳回＝人已确认"标签判错、框是正常文本"，若仍排除，则 D32 的"审批现场打标签转人工 → 清理队列消化"没有出口（驳回后照旧被排除，循环卡死）；已驳回的框视同普通框参与合并判定，D28／D30／D32 闭环自洽。**排除范围仅指 D38 的误识别正则标签**：`ocr_low_conf` **不排除**（它是"低置信"而非"误识别"），其标签按 D33c 的并集进入新块，两处一致。 |

## 6. 逐条技术现状与缺口

### 6.1 问题载体：标签体系扩建（D1、D2、D15、D17）

**现状**：`utils/block_tags.py::TAG_REGISTRY` 为声明式注册表（5 个类型），条目存 `utils/textblock.py::TextBlock` 的 `tags` 字段并随项目 JSON 自动持久化；程序自动挂标的先例见 `utils/block_tags.py::apply_ocr_confidence_tag`（由 OCR 模块在结果组装处调用）。标签**不进撤销栈**，只置未保存位。

**本议题的缺口与要点**

1. **"判为误杀"在程序标签上的动作不是"移除"而是"驳回标记"**（D28）。移除会被程序重算回来、且丢掉"已驳回"的记忆，故改为在条目上置 `reviewed`（可逆，见 D28）。"移除成本极低"只适用于**人工挂的**疑点标签（见第 5 点）。
2. **"确认该删"出口：一键批量删除（D27）。** 删除框属于**新出口**（要写 `proj.pages` + 撤销命令 + 脏页处理）；脏页问题由 D27 的"前期不主动处理脏页"原则消化；出口按 [AI辅助功能_规划](AI辅助功能_规划.md) §7 白名单原则登记。**撤销命令不能复用现成的 `ui/scenetext_manager.py::DeleteBlkItemsCommand`**——它只作用于**当前页**（按 `idx` 索引当前页 widget 与图像缓冲、且不写 `proj.pages`），跨页批量删除只能借鉴形态；其余现成基座与约束见 [泛用工作台_复核与拆分](泛用工作台_复核与拆分.md)。
3. **这类标签可能是标签体系第一个"没有 AI 动作出口"的类型**——AI 看图也认不出纯数字框是什么内容。因此它不需要 `consumes`／动作映射，只需要"确认／驳回"。
   **修正（2026-09-15）**：`utils/block_actions.py::BlockActionDef` 的 `consumes` 白名单方向是**动作 → 标签**（`actions_for_block` 只对 `consumes` 命中的块出按钮），所以"新标签没有动作出口"**天然成立、零改动**，无需为可选性做任何声明（此前判断说重了）。
4. **审阅状态的存放：就放在标签条目里，零新数据结构；机制为 `reviewed` 字段（D28）。** 依据是对"管线清空"的两层实测（见下）。理由：`source` 表达"标签从哪来"（事实）、`reviewed` 表达"人怎么看"（表态），两者正交，不应混用。保留 `source`、追加 `reviewed`；挂标处（`utils/block_tags.py::apply_ocr_confidence_tag` 与新增正则挂标）对带 `reviewed` 的条目跳过，即可在重跑 OCR 后存活。
5. **人工挂的疑点标签与程序挂的标签，审阅语义不同**（与 D17 的分工一致）：
   - 人工挂的疑点标签（`trans_confusing` / `trans_polish`）：**审阅 = 直接摘掉**，不需要状态字段。
   - 程序挂的标签（`ocr_low_conf` 及新增正则标签）：**不能靠摘掉**（会被重算回来，且丢失"已驳回"的记忆），因此需要 `reviewed` 状态（D28）。`utils/block_tags.py::set_tag` 已支持任意 `**extra`，是现成扩展点。
   - **两者的关系**：`reviewed` 是**程序标签条目的通用机制**（驳回为块级，同时作用于该块全部 program 条目，见 D28）；但**队列的入选依据只有误识别正则标签**——只带 `ocr_low_conf` 的块（§7 中非空的约 72 个）不进"误识别清理"队列，其出口是 `utils/block_actions.py` 的框级 OCR 校正动作。
6. **人工编辑即知情（D29）**：人工编辑某块文本后，清除该块全部 program 来源临时标签（`ocr_low_conf` + 误识别类），不做自动重判。注意标签不进撤销栈，撤销文本编辑不会恢复被清标签（可接受：重跑 OCR 会重算）。

**「管线清空」的两层语义（2026-09-15 核实，为第 4 点的依据）**

| 重跑范围 | `text` | `tags` | 代码位置 |
|---|---|---|---|
| 只重跑 OCR | 清空 | **保留** | `modules/ocr/base.py::OCRBase` 的 `run_ocr` 内 `blk.text = []`（`none_ocr` 除外） |
| 重跑检测 | 清空 | **全丢** | `ui/module_manager.py` 内 `self.imgtrans_proj.pages[imgname] = blk_list`，整页换新块对象 |

- 重跑检测时标签全丢，但仅当 `pcfg.module.keep_exist_textlines` 为真才会把旧块拼回（该字段默认 `False`，见 `utils/config.py`）。
- **结论：这个行为恰是所需语义。** 重跑检测连 `text` 都丢，"审阅状态跟着丢"自洽（重跑即从审阅起点重来）；而只重跑 OCR 时 `tags` 保留，且 `utils/block_tags.py::apply_ocr_confidence_tag` 对 `source != "program"` 的条目**直接 return 不覆写**——D28 的 `reviewed` 跳过逻辑照此模式加在挂标处即可。
- 由此**不需要改造管线**，也不需要新建的"忽略名单"结构。

### 6.2 批量"简单背景"纯色修复（D3）

**用户方案**：针对"简单背景"的框直接用纯色覆盖，跳过修复模型（模型反而可能把气泡边框识别进去）。项目内已有该逻辑（用户观察到的手动框选修复行为）。

**核实结论：判据已完整实现，且与目标只差一个分支。**

`modules/inpaint/base.py::InpainterBase` 的 `inpaint()` 逐块路径（**示意摘录，变量名与实参从简，判据链为准，实参见实现**）：

```python
enlarge_window(xyxy, im_w, im_h, ratio=1.7)            # 框外扩
ballon_msk, non_text_msk = extract_ballon_mask(im, msk) # 非文字像素掩码
average_bg_color = np.median(non_text_px, axis=0)       # 中位背景色
std_max = np.max(np.std(non_text_px - average_bg_color, axis=0))
inpaint_thresh = 7 if np.std(std_rgb) > 1 else 10       # 动态阈值
if std_max < inpaint_thresh:
    result[ballon_msk > 0] = average_bg_color           # 纯色覆盖
```

三点值得记录：

1. **"文字像素干扰色差判定"已被现有实现解决**——判据算在 `non_text_msk`（排除文字后的非文字像素）上。
2. 手动框选那条路（`ui/drawingpanel.py::inpaintRect`）复用同一套 `bub_dict`（`bground_rgb` / `need_inpaint`），纯色覆盖后 push `InpaintUndoCommand`，**是进撤销栈的**。
3. 管线里已有开关 `utils/config.py::ModuleConfig` 的 `check_need_inpaint`（运行对话框的 "Skip simple cases"）。

**精确缺口**：现有语义是「**简单块纯色 + 复杂块走修复模型**」，用户要的是「**简单块纯色 + 复杂块完全不动**」。**实现方式是在逐块路径的 `need_inpaint` 取真分支上新增一个"只处理简单块"的开关／入口（默认关闭），而不是改写该分支的默认行为**——正常跑管线时复杂块仍须走修复模型，无条件改写会破坏既有修复功能。判据、掩码提取、纯色填充、撤销命令全部现成。

**实现注意点**

- `inpaint_by_block=False` 那条路径是**整图判断一次**，只有逐块路径才是每块判断；批量做必须走逐块语义。
- 逐页处理**是程序遍历全书页**，不存在逐页人工干预的问题；用户已明确"只要能节约这些人力，多写点硬盘无所谓"，故允许落盘中间结果换速度。
- **判据一律算原图（D34）**：防止用户手动修过的复杂块在 inpainted 图上被误判为"简单"而遭纯色覆盖、毁掉手工成果；只写 `inpainted/` 层，跑完重载当前页显示，其余页照旧惰性。

### 6.3 批量合并相邻框（D8、D16）

**用户提出的顾虑**：文本检测后的框顺序对这些"应当合并的框"不连贯，可能是 (1,3,5,7,9) 的跳跃顺序；直接边合并边改列表会导致后续索引变动，顺序错乱。

**量化验证（实机样本：94 页 / 1565 框，仅跑过检测与 OCR）**

| 指标 | 数值 |
|---|---|
| 几何候选对总数 | 1042 |
| 索引相邻（gap 1） | 523（50.2%） |
| **索引跳跃（gap ≥ 2）** | **519（49.8%）** |
| 跳跃中 gap 2 / 3 / 4+ | 318 / 121 / 80 |
| 最大 gap | 16 |
| 合并组数（连通分量 > 1） | 435 |
| 每组框数（min / 中位 / max / 平均） | 2 / 3 / 19 / 3.0 |
| 涉及框数 / 全书框数 | 1323 / 1565（**84.5%**） |

**结论：用户的顾虑被数据证实，约一半的相邻关系在列表里是跳跃的**，因此"边扫描边合并"不可行，必须采用**两阶段**做法。样本中亦直接出现了用户描述的形态：`014.jpeg` 的一组候选索引为 `[0, 2, 4, 6]`。

**关键发现：`sort_by_grid` 不适用（见下）；而组级方向规则与"对成员跑 `sort_regions`"效果持平（94.3% vs 94.4%，差 3 对）——按 D41 自建组级规则、不复用 `sort_regions`。**

`utils/textblock.py::sort_by_grid` 的 docstring 是 "This solves the quadrant zigzag problem: blocks in the same semantic region stay contiguous, so **merge tools produce correct text order**"，字面看像"项目里已有专为合并场景准备的重排工具"，但用同一份实机样本实测后**不成立**。度量方式（组判据同上：同页、行高相近、重叠 > 0.6）：

- **成员连续**：该组成员在重排结果里是否落在连续的索引区间（决定合并块的位置有无歧义）。
- **组内一致**：组内两两先后是否符合阅读方向（逐对统计，共 1797 对）。

| 排序方案 | 成员连续 | 组内一致 |
|---|---|---|
| 现状（检测器输出顺序） | 48.5% | 94.0% |
| `utils/textblock.py::sort_regions` | 85.3% | **95.1%** |
| `sort_by_grid` 1×1（等价于纯"自上而下、自左而右"） | 91.3% | **48.1%** |
| `sort_by_grid` 2×2 RTL | 89.2% | 50.9% |
| `sort_by_grid` 3×3 RTL | 86.4% | 49.4% |

**`sort_by_grid` 为何不适用**：它的单元内排序写死为 `(y1, x1)`，`reading_dir` 只作用于网格单元之间。而本样本是竖排为主（`src_is_vertical` 为真的块 1332 / 1565，含竖排块的页 76 / 纯横排页 5），竖排的阅读方向是列自右向左，用 `(y1, x1)` 会把同组的列交错开——实测组内一致率因此塌到 48%。它的 docstring 承诺只在 LTR／横向四格漫画下成立。

**另一处必须澄清：「索引跳跃」不等于「顺序错乱」。** 现状顺序的组内一致率已达 94.0%，说明检测器输出本就接近阅读序（`modules/textdetector/detector_paddlev6.py` 内部已调用 `utils/textblock.py::sort_regions`；`modules/textdetector/detector_ysg.py` 同）。所以 519 个跳跃对的成因不是"列表乱了"，而是**空间上属于同组的两个框，在阅读序里本来就被别的框隔开**。两阶段的真正理由是**避免"边扫描边改列表"造成索引漂移**，而非"顺序需要修正"。

**组内拼接顺序（用户方案）**：用户方案 = 用**块的原文方向**（`utils/textblock.py::TextBlock` 的 `src_is_vertical`，非用户可改的渲染方向 `vertical`）决定组内拼接顺序（竖排 → 列自右向左；横排 → 行自上而下），方向由块顺序与全书统计共同判定。对同样 435 组实测：

| 组内顺序规则 | 逐对一致 |
|---|---|
| 直接沿用页级顺序 | 94.0% |
| **按组级方向规则（用户方案）** | **94.3%** |
| 对该组成员跑 `utils/textblock.py::sort_regions` | 94.4% |
| 按页级方向（只用整页判方向） | 91.4% |
| 按 `(y, -x)` 朴素排序 | 66.6% |

三条结论：

1. **用户方案成立**，且与 `sort_regions` 基本持平（1694 vs 1697，共 1797 对，差 3 对，在噪声内）。故取更透明、零外部依赖的**自建组级规则**（D41）。
2. **方向判定必须在组级做，不能在页级**：页级判定掉到 91.4%，因为同一页可能混排。
3. **方向本身的争议极小**——按各组自身顺序的单调性统计：竖排组中 x 递减（右到左）**391** 个、x 递增仅 **1** 个；横排组中 y 递增（上到下）31 个、y 递减 9 个。即"竖排 = 右到左"在本样本里是 391:1 的通例。用户设想的"全文方向统计投票"因此更适合当**交叉校验**，其真正价值是**把那 10 个反常组在审批行标注"顺序存疑"供人工留意**（占 435 组的 2.3%；D32 已定不设反常组特殊处理，标注是它唯一的作用）。**（D32：不做反常组特殊处理，改为审批现场"反转该组方向"按钮 + 问题块打误识别转人工。）**

**方案形态**：两阶段——

1. **规划阶段（纯计算，不改数据）**：几何聚类出候选组（**排除带"未驳回"误识别标签的框，D30**；已驳回的框视同普通框参与）→ 组级方向判定（以 `utils/textblock.py::TextBlock` 的 `src_is_vertical` 为主，块顺序交叉验证，全文投票兜底）→ 产出合并建议与审批材料。
2. **应用阶段（一次性重建）**：一次遍历重建整页块列表，**保留用户既有顺序、不自动重排**（见 D7），组内文本按方向规则拼接。

**已关闭项**：审批粒度 = 列表级（§8 留档第 2 条）；截图 = 成员框并集虚拟框 + 外扩（D31）；方向判定保留组级 + 审批现场"反转该组方向"按钮（D32）；写回细则（`text` 形态／样式来源／`tags` 并集／误聚阈值）见 D33。

**截图外扩量的数据默认值**：组包围盒中位 83×148 px；组到邻框的间隙中位 300+ px、p10 约 80–93 px、最小 0–1 px（相邻气泡会贴住）。故**默认外扩 = 组包围盒短边的 50%（约 40 px）**（D31 直接引用此值），硬上限为"碰到邻框即停"。**注意**：p90 组宽 200 px、最大 1827 px（该组在 `057.jpg`，其页为 2063 px 宽的跨页图，组宽占该页 89%，属跨栏误聚，不是"超过页宽"；按 D33d 默认不勾选 + 警示标，阈值在设置内可调；实测：85% 默认值在 435 组里仅命中 2 组，均为此类——另一组为 `093.jpg` 的 903×117／页 1015）。

### 6.4 批量框扩张（D5）

纯几何计算，零 AI。只扩**渲染区域**，不动擦除区域（检测模型自身的扩张量对修复已够用）。

**两项已定案**

1. 扩张上限：**"碰到邻框即停"**（D5；`xyxy` 同步变动已接受，D36）。
2. 执行顺序：**在合并之后**（合并产出才是嵌字用的最终框）——作 D16 的导航默认顺序；运行时不强制、可跳步（D37）。

**交互**：除批量外支持单块调整，拟借鉴 PS 的 Alt + 拖拽 = 以中心为基准缩放，用户已熟悉，学习成本为零。

**补充**：字段改动接受 `_bounding_rect` 与 `xyxy` 同步变动（D36，沿用现有 sync 路径，与手动拖拽行为一致）；任务顺序不强制、跳步弹窗提示未处理数（D37）。

### 6.5 翻译策略"自动"档（D6）

**用户诉求**：功能项太多太杂，很难判断用哪个；希望用户只管页数、术语表这类确定性输入，策略由程序／AI 判断。

**建议分两步走**

1. **先规则化（零 AI）**：是否有术语表 → 是否注入；语言对 → prompt 选择；竖排/横排 → 排版分支；有无 vision profile → 是否允许看图；页数/块数规模 → 批量或逐页。这些**几乎全部可判定**，不需要 AI 参与。
2. **AI 只兜底真模糊项**，且选择范围收敛成有限枚举，不是自由选择。

更彻底的做法：配置项增加"自动"档并**默认自动**、用户可覆盖——连"要不要选"这个问题都省掉。按 D6，启用后必须**在界面备注其可能执行的行为**以给用户预期。

**（D37：涉及新增功能，延后，不进入本次实现范围。）**

### 6.6 自动排版（用户草案，需深入讨论）

**用户草案**：以人工选定的默认样式为基准，支持"文本量大时适当调整字号"（原文排版本身就常这么做）。翻译完成并调整换行后，允许 AI 获取默认样式字号**一定误差范围内**的占用空间（按需请求：先用默认字号算是否足够，不够则通知 AI 需要向下调整，**空间计算由纯代码完成**）；代入文本框判断是否装得下，装不下则启用**溢出裁剪**保证文本框不被破坏，并标记交用户处理。

**好消息：已有的比预期多。** `ui/text_engine/horizontal_layout.py` 与 `ui/text_engine/layout.py` 中的 `shrink_width` / `shrink_height` 就是排版度量——引擎**已经能算出"这段文字在该字号下占多大"**。所以"装不装得下"的检测是纯计算，无需重建字体度量，缺的只是"按溢出反向调字号"的迭代层。

**必须分清的一点**：「填不满」与「塞不下」是两个不同问题，只有一者能靠排版解决。

- **填不满**（文字比框小）→ 放大字号，但有上限（漫画正文有习惯字号区间）→ 到顶仍不满，本质是**译文比原文短**，只能改译文。
- **塞不下**（文字比框大）→ 缩小字号，但有下限（可读性）→ 到底仍塞不下，本质是**译文比原文长**，只能改译文。

即：排版方案能覆盖"轻微不匹配"的多数情况；**"极端不匹配"——恰是用户所说最折磨的部分——排版解决不了**。

**建议拆成两件可独立验证的事**

1. **排版侧（纯计算）**：框内锚定 + 字号在上下限内自适应 + 溢出／欠满检测。风险在字体度量与换行重算的一致性（`ui/text_engine/horizontal_layout.py` 体量大，含换行、标点、竖排规则）、竖排、标点规则。`utils/fontformat.py::FontFormat` 目前有 `alignment` 但**无垂直居中字段**，此块需改动。
2. **译文侧（AI 定点）**：溢出／欠满被检测出来后**挂标** → 进工作台队列 → AI 在保持语义前提下"压到 N 字以内／扩到 N 字左右" → 确认卡。**正好复用现有标签 + 框级动作闭环**，无需新架构。

用户对 AI 介入深度的预期已明确："没指望现有的 AI 和项目功能能够自主处理复杂情景，只要保证在工作良好的舒适区内尽可能减少人的操作即可。"

**（D37：涉及新增功能，延后，不进入本次实现范围。）**

## 7. 问题框实测规模与现有覆盖（D9）

用 §6.3 的同一份实机样本（94 页 / 1565 框，只跑过检测与 OCR，检测器 `ppocrv6_onnx`）统计"程序可判定的问题框"：

| 类别 | 数量 | 备注 |
|---|---|---|
| 空文本 | 36 | **36 个已全部带 `ocr_low_conf` 标签**（其中 13 个 score 为 0.0） |
| 纯数字 | 20 | 如 `8` / `166` / `11` / `4` |
| 纯符号 | 15 | 如 `?` / `……` / `①` / `#` / `—` |
| 无假名/汉字（疑似 OCR 乱码） | 92 | 如 `SS` / `H1` / `anad`（含上面部分纯数字） |
| 四类去重合计 | **128（占 8.2%）** | 与 `ocr_low_conf` 集合（共 108 个）部分重叠 |
| 已有 `ocr_low_conf` 的块 | 108 | 其中非空文本约 72 个（即"有内容但低置信"） |

**关键结论（修正起因中的假设）**：用户最初举例的"置信度低且没识别出内容"**已被现有实现覆盖**——空文本块 100% 自动挂上 `ocr_low_conf`（程序来源，见 `utils/block_tags.py::apply_ocr_confidence_tag`）。真正未被覆盖的是**纯数字／纯符号／拉丁乱码**：这类块 OCR 能识别出字符、置信度并不低，`ocr_low_conf` 抓不到，正需要新增正则标签（D2）。第三类是"有内容但低置信"（`ocr_low_conf` 中非空的约 72 个），其出口在 `utils/block_actions.py` 的 OCR 校正动作已存在，仅限单选单块。

**对工作台队列规模的启示**：全书需人工审查的条目约 128 个（平均每页 1.4 个），一次性列成清单的规模可接受。**这 128 个就是"误识别清理"队列的规模**（按 D38 的误识别标签覆盖的块去重计）；`ocr_low_conf` 的块（108 个，其中 36 个空文本已含在四类内）**不单独入队**，其出口是框级 OCR 校正动作（见上段）。

**注意**："无假名/汉字"会误伤漫画中真实存在的拉丁文本（英文拟声词、外来语），这正是用户设计"人审查误杀"的必要性所在——该类别是四个判定里最需要人工过滤的一类。

### 9.1 一级导航复用 `ui/mainwindowbars.py::LeftBar`（D22／D25）

### 9.6 批量"简单背景"纯色修复（D3）

- `modules/inpaint/base.py::InpainterBase` 的 `inpaint(img, mask, textblock_list=None, check_need_inpaint=False)`：`inpaint_by_block` 为真且传了 `textblock_list` 时走逐块路径。逐块时 `need_inpaint` 初值 `True`，若 `std_max < inpaint_thresh` 则置 `False` 并**纯色覆盖**；末尾 `if need_inpaint:` 才走修复模型。**改动点就是这个末尾分支**——但须做成**新增开关（默认关闭＝保持既有行为）**：开启时"取真的块跳过模型"，关闭时照旧走模型。**不可无条件改写**。

### 9.7 批量合并（§6.3 的实现层）

- 现有手动合并：入口是右键／饼菜单的 `merge`（`enabled = 选中 ≥2`）与快捷键 `merge_blks`；调用链为 `ui/canvas.py::Canvas` 的 `merge_textblks` 信号 → `ui/scenetext_manager.py::SceneTextManager` 的 `on_merge_textblks` → `_build_merged_blk`。
- `_build_merged_blk` 的事实：按块 `idx` 排序；新框坐标取各 item `absBoundingRect()` 的**并集**；`merged.text` 是**每块一个元素的列表（非拼接）**；`merged.translation` 用换行连接；**样式（含 `tags`）来自对第一个块的深拷贝**；**无任何竖排／右到左感知**；最后置 `merged` 标记并清 `region_mask` 与 `region_inpaint_dict`。**（D33：批量合并不复用此函数——`text` 默认逐行展开、样式来源按列表序、`tags` 取成员并集、方向感知排序，均需新写。）**
- **写回是"只改视觉层"**：`MergeTextBlksCommand` 只操作 `textblk_item_list` 与 `pairwidget_list`，`proj.pages` 由之后的 `ui/scenetext_manager.py` 的 `updateTextBlkList` 整页重建赶上（后者只处理当前页、整页替换）。**（D40：批量操作不走这条"视觉层先行"路径——它按五步顺序写回，且禁止事后再调 `updateTextBlkList`，否则新数据会被旧面板值覆盖。）**
- **页代数**：批量重建某页块列表**必须**调用 `utils/proj_imgtrans.py::ProjImgTrans` 的 `bump_page_generation`（否则按块锚点记账的端点快照会落到错误块）；若同时重写图像缓冲，再加 `bump_page_image_generation`。另有 `ui/canvas.py::Canvas` 的 `invalidate_text_history_for_page` 供"原地重写、块对象不换新"的路径使用。
- **`sort_regions` 既有缺陷**：`utils/textblock.py::sort_regions` 在 `right_to_left` 传 `None` 时以 `nv / nr > 0` 推断方向（**分母是总块数**，1 个竖排块即判右到左；且读的是 `vertical` 而非 `src_is_vertical`）。批量合并自建组级方向判定、不依赖它（D41：不修，缺陷留待后续单独处理）。
- 口径参考：`tmp/analyze_merge2.py` 里的 `order_sort_regions` 做的就是"组内跑 `sort_regions`"，可用于**口径比对**。注意 `tmp/` 被 `.gitignore` 排除、**不在版本控制内**（随时可能被清理），不可作为交付依赖；且 D41 已定自建组级规则、不复用 `sort_regions`。

### 9.8 撤销体系（D21：按操作类型分）

- 两套栈：`ui/canvas.py::Canvas` 的 `draw_undo_stack` 与 `text_undo_stack`。路由在 `push_undo_command`：`image_history` 为真的命令走 `push_image_command` 并**进全局 `text_undo_stack`**（跨页）；文本编辑模式进文本栈；绘制模式进绘制栈；都不满足则丢弃。
- **抓图像切片的命令**（三个都 `np.copy` 图像，但**路由判据是 `image_history` 标记，不是"是否含图像载荷"**）：`ui/drawing_commands.py::InpaintUndoCommand`（**`image_history = True`**，构造期深拷贝矩形切片，且有 `try_absorb` 聚合同区域连续修复）、`ui/drawing_commands.py::RunBlkTransCommand`（特定模式下抓取每块修复区域的前后图，**无该标记**）、`ui/drawing_commands.py::StrokeItemUndoCommand`（单笔涂鸦位图，**无该标记**）。
- → **划分点**：仅 `InpaintUndoCommand` 属"进全局栈的重载荷"；另两个图像命令不进全局栈（批量删框若照抄它们，得不到页标签 + 代数保护）；其余文本类命令（`ui/textedit_commands.py` 与 `ui/scenetext_manager.py` 中的命令）都是纯文本前后快照，留内存即可。
- **D35 的版本仓库就是"批量落盘撤销"的现成基座**：`utils/batch_versions.py::BatchVersionStore` 在操作前写一版（项目数据 + 受影响矩形的像素前图）、按 LIFO 取最新一版覆盖并消耗、带 `dirty_pages` 清单与 UI 回滚条（`ui/global_search_widget.py`）；查找替换与工作台批量任务共用同一套。**（归并说明：查找替换原走 `utils/proj_imgtrans.py::ProjImgTrans` 的单槽 JSON 快照（`*.batch_backup.json`，项目 JSON 同级、会话内有效、**只快照 JSON 不含像素**——纯色修复改的是 `inpainted/`，那种快照撤不回像素）；2026-09-16 并入本机制后删除。D35：版本轮转制，默认 1、上限 5，项目目录内子目录；像素版只存前图。）**

### 9.10 关键代价与结构数据（沿用实测）

- **撤销载荷**：全部框面积 8.48 M px，按修复管线 `ratio=1.7` 放大后 **14.42 M px**；内存快照（前后各存 img+mask）≈ **110 MB**，只存前图 ≈ **55 MB**。
- **磁盘**：`inpainted/` 94 个文件共 **140.6 MB**（平均 **1.53 MB/页**）；同页 `result/` 仅 0.67 MB/页。矩形区域落盘（仅各框前图）估约 **43 MB**。
- **布局**：主窗口是纯 `QHBoxLayout` + `setFixedWidth`，宽度常量在 `ui/mainwindow.py::MainWindow`（页列表 250、全局搜索 300、工作台 460；右栏 360 为字面量）。可用宽 = `屏宽 − 48 − 工作台宽 − 5 − 360`。画布无最小宽度约束会被自动挤压，但窗口有下限 `setMinimumWidth(屏宽 // 2)`（1920 屏即 960）；D24 定稿维持 460 后不触及该下限。**（D24：适度加宽，默认维持 460。）**
- **缺图**：`utils/io_utils.py::imread` 走 PIL，**返回 RGB（不是 BGR）**，文件不存在返回 `None`；批量截图须先自检存在并对 `None` 兜底。
