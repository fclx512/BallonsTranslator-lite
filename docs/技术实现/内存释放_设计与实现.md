# 手动释放内存（卸载模型 → 销毁 CUDA 上下文 → 交回工作集）

**入口**：设置页 Models → Management 的「释放内存」按钮，**用户手动点、点前弹确认**。
代码分两层：逻辑在 `utils/memory_release.py`（无 Qt，可注入替身，单测覆盖编排），
提示与忙闲判据在 `ui/mainwindow.py::MainWindow`。

## 1. 为什么要做：实测数字（2026-09-17，本机 RTX + torch 2.13+cu132）

ppocrv6 检测 + paddleocr_v6 OCR **各跑一次**（都 `device=cuda`），读数＝进程工作集
（`GetProcessMemoryInfo`，即任务管理器看到的"内存"）：

| 步骤 | 工作集 | 说明 |
|---|---|---|
| 引擎导入 + 开项目（未用 CUDA） | 590 MB | 基线 |
| 跑完一轮 CUDA | 1503 MB | 用户报的"600 → 1700"同一现象 |
| 卸载全部模型 + `gc` | 1503 MB | **现有「卸载全部模型」按钮：几乎没用**（只掉 0~75MB） |
| `torch.cuda.empty_cache()` + `ipc_collect` | 1503 MB | 也没用（占的不是 torch 池） |
| `cudart!cudaDeviceReset()` | 1295 MB | **−208MB，真还**；GPU 侧完全归还 |
| `psapi!EmptyWorkingSet()` | **111 MB** | **交回**（语义见 §2） |
| 之后再用一次 CUDA | 420 MB | 首次 0.33s、第二次 0.01s |

两处**推翻旧判断**（旧结论写在 `docs/技术实现/区域再检测_设计与实现.md` 的内存一节）：

1. **不是"拉起了一个 CUDA 进程"**：CUDA 上下文与 ORT 会话都在本进程内。工作集里那部分
   还包括被加载进来的驱动侧 DLL（模块工作集合计 350 → 407MB，`cublasLt64_13.dll` 单项
   就 144MB），叠加私有内存才到 1500MB。
2. **不是"只能关进程退还"**：只对"真 free 到进程外"成立。进程内能还两档，合计
   1503MB → 111MB；要"确定性真释放到进程外"才需要子进程（本机重建代价 ≈2~3s：
   引擎导入 1.8s + 首个 CUDA 会话 0.3~0.8s，见 §4"不做的事"）。

## 2. 三步的分工与语义（别混）

| 步骤 | 函数 | 效果 | 语义 |
|---|---|---|---|
| 卸载模型 | 调用方给的 `unload` 回调（`ui/module_manager.py` 的 `unload_all_models`） | 0~75MB | 真卸载，但**几乎不还内存**；它是 reset 的前置条件 |
| 销毁 CUDA 上下文 | `utils/memory_release.py` 的 `release_cuda_context` | −208MB | **真释放**（驱动资源与显存完全归还） |
| 交回工作集 | `utils/memory_release.py` 的 `return_working_set` | −1184MB | **交回，不是 free**：页退回系统备用内存，DLL 的干净文件映射页系统可立即丢弃给别的程序、私有脏页进 pagefile；页表映射还在，**下次访问要 fault in** |

对外文案一律按上表写（"真释放"与"交回"分开表述）——混为一谈会被当成假释放。

## 3. 安全铁律（全部有实测依据）

1. **先 `empty_cache` 再 reset**：不先清就 `cudaDeviceReset`，torch 会拿到失效指针——
   实测 `matmul` 报 `CUBLAS_STATUS_INTERNAL_ERROR`，随后任何分配报
   `an illegal memory access was encountered`；先清再 reset 则 torch 与 ORT 重建后都正常。
2. **不能有 CUDA 活在跑**：管线、四个"切换模块"线程、区域再检测的后台检测线程（其检测器
   可配成 CUDA）。`ui/mainwindow.py::MainWindow` 的忙闲判据命中时**直接拒绝**并提示等待，
   不冒险 reset。
3. **卸载失败就不 reset**：`unload_all_models` 返回 `False`（卸载过程中抛异常）时说明可能有
   活跃 CUDA 会话，此时**只交回工作集**，并在结果提示里说明"CUDA 上下文没动"。
4. **不自动触发**：交回工作集会把界面也要用的页换出去，紧接着的交互可能卡一下（毫秒级），
   所以是手动按钮，不做成"跑完自动"。

## 4. 提醒用户"接下来会怎样"（点确认前必须说清）

确认框（`ui/mainwindow.py::MainWindow` 的 `on_release_memory`）写三条：

- 下一次跑管线／AI 修复会**重新加载模型并重建 CUDA 会话**，首次慢几秒；
- 释放后的**首次交互可能短暂卡顿**（Windows 把数据换回来）；
- 释放期间保持空闲，别同时开跑。

结果用通知中心 toast 报读数（`工作集 {before} MB → {after} MB`），失败路径各有一条
warning 文案（卸载失败 / 上下文没销毁）。

**不做的事**：① 不自动在每次跑完管线时释放；② 不做子进程隔离——那才能"真释放到进程外"
（重建 ≈2~3s），但要把管线阶段搬出 GUI 进程，收益不抵架构改动；③ 不新增第二套清缓存语义：
`modules/base.py` 的 `soft_empty_cache` 仍是管线侧的日常清理，本按钮只是"用户按需要回内存"。

## 5. 验收

- 单测 `tests/test_memory_release.py`：步骤顺序、读数记录、**卸载失败不做 reset**、
  单步异常不外抛、`empty_cache` 排在 `cudaDeviceReset` 之前、设备忙则放弃（全用替身，不碰真 CUDA）。
- 真机复核：探针模板与读数口径见技能 `windows-app-memory-attribution`（§1 读数、§6 释放/交回），
  跑引擎脚本要用 `ballontrans_pylibs_win/python.exe`。
- GUI 侧要人工确认两件事：忙闲判据真的挡住了管线运行中的点击；释放后**下一次跑管线照常**
  （模型重新加载、CUDA 会话重建、结果与释放前一致）。
