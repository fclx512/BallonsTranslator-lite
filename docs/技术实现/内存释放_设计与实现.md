# 手动释放内存（卸载模型 → 交回工作集）

**入口**：设置页 Models → Management 的「释放内存」按钮，**用户手动点、点前弹确认**。
代码分两层：逻辑在 `utils/memory_release.py`（无 Qt，可注入替身，单测覆盖编排），
提示与忙闲判据在 `ui/mainwindow.py::MainWindow`。

**刻意不做的事**：不销毁 CUDA 上下文（2026-09-20 拍板删除，原委见 §4）。

## 1. 为什么要做：实测数字（2026-09-17，本机 RTX + torch 2.13+cu132）

ppocrv6 检测 + paddleocr_v6 OCR **各跑一次**（都 `device=cuda`），读数＝进程工作集
（`GetProcessMemoryInfo`，即任务管理器看到的"内存"）：

| 步骤 | 工作集 | 说明 |
|---|---|---|
| 引擎导入 + 开项目（未用 CUDA） | 590 MB | 基线 |
| 跑完一轮 CUDA | 1503 MB | 用户报的"600 → 1700"同一现象 |
| 卸载全部模型 + `gc` | 1503 MB | **现有「卸载全部模型」按钮：几乎没用**（只掉 0~75MB） |
| `torch.cuda.empty_cache()` + `ipc_collect` | 1503 MB | 也没用（占的不是 torch 池） |
| `psapi!EmptyWorkingSet()` | **111 MB** | **交回**（语义见 §2）——**大头在这一步** |
| 之后再用一次 CUDA（ORT 会话） | 420 MB | 首次 0.33s、第二次 0.01s |

> 表里少了当年的 `cudart!cudaDeviceReset()` 一行（工作集 1295MB）——那条能力**已删除**：
> 它只多还 ~200MB，却不可逆地毁掉本进程的 CUDA，详见 §4。

两处**推翻旧判断**（旧结论写在 `docs/技术实现/区域再检测_设计与实现.md` 的内存一节）：

1. **不是"拉起了一个 CUDA 进程"**：CUDA 上下文与 ORT 会话都在本进程内。工作集里那部分
   还包括被加载进来的驱动侧 DLL（模块工作集合计 350 → 407MB，`cublasLt64_13.dll` 单项
   就 144MB），叠加私有内存才到 1500MB。
2. **不是"只能关进程退还"**：只对"真 free 到进程外"成立。进程内靠 `EmptyWorkingSet`
   就能从 1503MB 掉到 111MB；要"确定性真释放到进程外"才需要子进程（本机重建代价 ≈2~3s：
   引擎导入 1.8s + 首个 CUDA 会话 0.3~0.8s）。

## 2. 两步的分工与语义（别混）

| 步骤 | 函数 | 效果 | 语义 |
|---|---|---|---|
| 卸载模型 | 调用方给的 `unload` 回调（`ui/module_manager.py` 的 `unload_all_models`） | 0~75MB | 真卸载，但**几乎不还内存**；它的价值是让 trim 时少留脏私有页（GPU 侧也顺带空出来） |
| 交回工作集 | `utils/memory_release.py::return_working_set` | −1000MB 量级 | **交回，不是 free**：页退回系统备用内存，驱动/DLL 的干净文件映射页系统可立即丢弃给别的程序、私有脏页进 pagefile；页表映射还在，**下次访问要 fault in** |

对外文案一律按上表写：本按钮的效果是**交回**，不写"真释放内存"——混为一谈会被当成假释放。

## 3. 安全铁律（都有实测依据）

1. **不能有 CUDA／推理活在跑**：管线、四个"切换模块"线程、区域再检测的后台检测线程
   （其检测器可配成 CUDA）。`ui/mainwindow.py::MainWindow` 的忙闲判据命中时**直接拒绝**
   并提示等待。
2. **先卸载再交回**：卸载回调抛异常或返回 `False` 时照常走 trim（两步互不依赖），但结果
   提示换成 warning 文案——读数会不好看，用户得知道为什么。
3. **不自动触发**：交回工作集会把界面也要用的页换出去，紧接着的交互可能卡一下（毫秒级），
   所以是手动按钮，不做成"跑完自动"。

## 4. 为什么不做"销毁 CUDA 上下文"（2026-09-20 实测后删除）

这一版之前，按钮还有第二支 `cudart!cudaDeviceReset()`（"真还 ~170~208MB"）。用户报
「点了释放内存之后 paddleocr_vl_manga 再也跑不起来」后复现，结论是**这个能力不能要**：

| 现象 | 实测 |
|---|---|
| `torch.cuda.is_available()` | **仍返回 `True`**（`is_initialized()` 也是） ⇒ 常规判据全部失效 |
| 第一次真实分配（`torch.zeros(4, device='cuda')`） | 报 `Torch.AcceleratorError: CUDA error: invalid argument`（`cudaErrorInvalidValue`） |
| 同一段代码另一次 | **进程直接段错误**，exit `0xC0000005`（整个应用没了） |
| 进程内恢复 | `torch.cuda.init()` / `set_device` / `empty_cache` / `synchronize` / `_cuda_clearCublasWorkspaces()` / 直调 `cudart` 的 `cudaSetDevice`/`cudaFree(0)` 全试过——**没用**，失败点就是第一次分配本身，连"试完再看一眼"的机会都没有 |
| 加载 torch 模型 | `AutoModelForCausalLM.from_pretrained(...).to('cuda')` 在 `.to()` 里就炸（用户看到的"运行错误"） |

真还的量级只有 **−71 ~ −166MB**（取决于当时驻留多少），代价是**本次会话的 GPU 模型全部
不可用、必须重启应用**，还可能把进程打崩。用户实测后确认：**正常交回就够了**，故整条
路径（含配套的进程级标记与模块侧拦截）已删除，并由
`tests/test_memory_release.py::RemovedCapabilityTest` 钉住"别加回来"。

真机复算与全部读数：`scripts/probes/release_cuda_context_aftermath.py`
（它同时验证"不 reset 时 torch 与 `paddleocr_vl_manga` 照常"：工作集 832 → 4.5MB 之后，
模型加载 4.2s、识别正常）。

> 真要"确定性释放到进程外"（连驱动侧显存也归零），唯一干净的做法是把这段工作放进
> 子进程、然后结束子进程——重建 ≈2~3s。这需要把管线阶段搬出 GUI 进程，收益不抵架构改动。

## 5. 提醒用户"接下来会怎样"（点确认前必须说清）

确认框（`ui/mainwindow.py::MainWindow` 的 `on_release_memory`）写三条：

- 下一次跑管线会**重新加载模型**，首次慢几秒；
- 释放后的**首次交互可能短暂卡顿**（Windows 把数据换回来）；
- 释放期间保持空闲，别同时开跑。

结果用通知中心 toast 报读数（`工作集 before MB → after MB`），失败路径各有一条 warning
文案（卸载失败 / 工作集没交回）。

**另外不做的事**：① 不自动在每次跑完管线时释放；② 不做子进程隔离（理由见 §4 末）；
③ 不新增第二套清缓存语义：`modules/base.py` 里的 `soft_empty_cache` 仍是管线侧的日常清理
（它只管 torch 池，不动工作集），本按钮只是"用户按需要回内存"。

## 6. 验收

- 单测 `tests/test_memory_release.py`：步骤顺序、读数记录、单步异常不外抛、trim 可关、
  `RemovedCapabilityTest` 钉住"销毁 CUDA 上下文"不再存在（全用替身，不碰真 CUDA）。
- 真机复核：`scripts/probes/release_cuda_context_aftermath.py`——期望
  **释放后 torch 分配/matmul 照常、`paddleocr_vl_manga` 加载（约 4s）与识别照常**；
  末尾那段"若销毁上下文会怎样"只作历史证据（它可能段错误，故放最后）。
  读数口径见技能 `windows-app-memory-attribution`（§1 读数、§6 释放/交回）。
- GUI 侧人工确认两件事：忙闲判据真的挡住了管线运行中的点击；**释放之后下一次跑管线照常**
  （模型重新加载、结果与释放前一致）。
