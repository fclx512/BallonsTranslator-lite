# 撤销体系底层重构计划

> 状态：**计划待评审，未执行**（2026-09-02 撰写）。依据为同日的撤销逻辑专项排查：离线复现台证据齐全，根因已定位并复现。本文档同时记录两个改进方向——**方向甲（渐进修补）作为回退保险路径**、**方向乙（彻底重构）作为主路线**；执行者倾向方向乙，方向甲用于乙出现重大问题时的退路。

---

## 一、问题定性（排查结论）

### 1.1 现状架构：一个文本块横跨三层撤销载体

| 层 | 载体 | 写入方 | 回退方式 |
| --- | --- | --- | --- |
| item 文档栈 | 每个 `TextBlkItem` 内部 QTextDocument 自带的 undo 栈 | 画布直接键入、面板格式化（char format 类 setter 全部以文档编辑形式落盘）、镜像对账 | 由命令层逐块"排水" |
| canvas 命令栈 | `ui/canvas.py` 的 `text_undo_stack`（QUndoStack） | `ui/textedit_commands.py::TextItemEditCommand` / `ui/textedit_commands.py::TextEditCommand` / 结构操作命令 | QUndoStack 标准撤销，04feaf8 起格式化命令由手势宏聚合 |
| panel 文档栈 | 右侧 `TransTextEdit` / `SourceTextEdit` 的 QTextDocument undo 栈 | 面板键入、画布→面板镜像同步 | 由命令层逐块"排水" |

命令层的每条命令本质是**桥接**：undo 时对 item 文档与 panel 文档各调用一次文档级 `undo()`（回退一个 undo 块）。整个体系依赖一个核心假设：

> **canvas 命令 ↔ 每份文档恰好一个 undo 块，且两侧块序一致。**

所有已确认缺陷的本质都是这个假设被打破。

### 1.2 确认缺陷清单（按破坏力排序）

**① 跨事务并块（根因，已复现）**。面板连续键入被 Qt 自动合并（`old_undo_steps` 无增量 → `new_steps==0`），镜像对账 `ui/textedit_commands.py::sync_text_by_diff` 据此以 `joinPreviousEditBlock()` 把本次文本编辑**无条件并入 item 文档的最后一个 undo 块**。若最后一块是格式化事务（改字号/字重/行距/颜色等都会产生文档块），文本编辑被缝进格式块，后果三连：

- 文本撤销与格式撤销纠缠：Ctrl+Z 退字号连带退文本，或反之；
- 双文档块结构分叉（pdoc 一块、item 文档多块），命令层"各退一块"从第一步就退错内容；
- 本次键入在画布栈上**没有自己的命令**（pdoc 无新步 → `push_undo_stack` 信号不发射），物理上无法单独撤销。

该机制由 6e2e7d5（全文差异对账）引入，**早于 04feaf8**，但近期格式化相关批次让它显形。

**② 伪造计步切断手势宏（04feaf8 新增）**。镜像路径的 `ui/scenetext_manager.py::on_propagate_textitem_edit` 在对账发生变化时调用 `ui/canvas.py::push_text_command`（command=None，仅推进计数），而该入口会先触发 `ui/canvas.py::_close_format_gesture()`。改字号后只要在面板打一个字，悬开的格式化手势宏就被无声切碎。

**③ 记账翻转（04feaf8 新增）**。`ui/scenetext_manager.py::on_push_textitem_undostack` 旧代码 `update_pushed_step=is_formatting`（键入 False、格式化 True，与"键入 = 命令(False)+伪造步(True) 各计一步"的旧约定配套）被改为键入 True、格式化 False。结果：画布键入**双计步**、格式化**零计步**，`num_pushed_textstep` 与栈位置漂移，脏状态判定（保存提示、`ui/canvas.py::text_change_unsaved`、批量替换回滚判定）失真。

**④ 次要隐患**。

- `ui/text_engine/item.py::set_cursor_cfmt` 在 `merge_char=True` 分支结束时无条件把 `block_change_signal` 复位为 False，不保存外层旧值，嵌套抑制可被打破；
- 一次 `setFontSize` 产生 2~3 个文档步（实测），`num_steps` 记账松散，靠 Qt 块语义兜底；
- `ui/canvas.py::clear_undostack` 在宏合成期间清栈落在 Qt 未定义边界上（当前版本实测能兜住，但属踩线）。

### 1.3 复现证据（离线复现台）

复现台构成：offscreen 平台 + 真实 `Canvas` / `TextBlkItem` + 面板编辑器替身（复刻 `ui/textedit_area.py::handle_content_change` 的发射语义：`propagate_user_edited(joint_previous)` 与 `push_undo_stack(new_steps)`）+ 按 `on_push_textitem_undostack` / `on_push_edit_stack` 布线。序列「面板键入 A → 改字号 30 → 面板键入 B → Ctrl+Z ×3」：

| 步骤 | 期望 | 实际 |
| --- | --- | --- |
| 面板键入 A | 栈 +1 命令 | 正常 |
| 改字号 30 | — | item 文档 +2 步，宏开启 |
| 面板键入 B | B 可独立撤销 | B 经 `joinPreviousEditBlock` 并入格式文档块；**栈上无 B 的命令** |
| Ctrl+Z ① | 只退 B | 字号+B 一起退；**面板仍显示 AB（失同步开始）** |
| Ctrl+Z ② | 退字号 | A+B 一起退（面板侧 A+B 合并块被整体回退） |
| Ctrl+Z ③ | 退 A | 落空（栈已耗尽） |

纯 canvas 键入、纯面板键入、格式化宏聚合在无交错时均正常——问题只在**交错**时爆发。已验证 Qt 本身语义无问题（宏 push 调 redo、undo 逆序、合成中 clear 可自愈），病灶全部在应用层耦合。

### 1.4 根因归纳：为什么"只修 ①"走不通

pdoc 侧的 Qt 自动合并发生在过去且**无法事后拆块**（Qt 没有拆块 API）。只要命令层继续以"文档 undo 块"为排水单位、格式化继续以文档变更形式与键入共享同一文档栈，块边界错位就必然从别的缝里回来。镜像对账的 `joinPreviousEditBlock` 正是为了追平两侧块结构而生，但它追的是 pdoc 侧的合并状态、作用在 item 侧文档上，两端控制权分裂导致追平机制本身成为纠缠源。**这是支持"彻底重构"的核心论据。**

## 二、目标行为定义

1. 文本键入：连续键入聚合为一个撤销步（文本编辑器习惯）；输入停顿、失焦、选区变化、模式切换断开会话。
2. 格式化手势：一次手势（含实时预览的全部中间值）= 一个撤销步；多选块一次手势 = **一个**撤销步（PS 习惯，保住 04feaf8 的成果）。
3. 撤销/重做永不落空、永不回退错对象；任何操作序列后画布与面板文本保持一致。
4. **修改字号的实时预览保留**——重构的是提交语义（手势结束才落撤销步），不是预览本身。
5. 与批量替换快照回滚（GlobalReplaceApplier 体系）继续分治，不并入本体系。
6. 绘制栈（draw_undo_stack）不在本次范围。

## 三、方向甲：渐进修补（回退保险路径）

四项独立小修，互不依赖，可随时单独落地与出货，也是方向乙中止后的底线方案。

### 甲-1 记账恢复（对应缺陷 ③）

恢复 `ui/scenetext_manager.py::on_push_textitem_undostack` 的旧 `update_pushed_step` 约定：键入命令走 False（脏计步由伪造步承担）、格式化走 True。改动一处，风险极低，立刻修复脏状态漂移。

### 甲-2 抑制复位修复（对应缺陷 ④）

`ui/text_engine/item.py::set_cursor_cfmt` 改为保存/恢复 `block_change_signal` 旧值（与文件内其他抑制点同样的 try/finally 模式）。

### 甲-3 伪造计步不切手势（对应缺陷 ②）

`ui/canvas.py::push_text_command` 对 command=None 的纯计步调用不触发 `_close_format_gesture()`（或为纯计步单开入口，绕过手势边界逻辑）。

### 甲-4 纠缠缓解（对应缺陷 ①，**明确其不彻底性**）

在 item 上维护"最后一个文档块是否为镜像块"标记（镜像同步置位、一切非镜像写入清位），`sync_text_by_diff` 的 joint 分支仅在标记成立时 `joinPreviousEditBlock`。局限：pdoc 侧的合并无法回拆，标记不成立时两侧块结构**仍然分叉**（pdoc 已合并、item 未合并），只能把错位窗口从"跨事务"收窄到"burst 边界"，无法闭合。这正是 1.4 节的结论。

## 四、方向乙：彻底重构（主路线，推荐）

### 4.0 终局图景：单栈快照命令制

- item 文档与 panel 文档一律 `setUndoRedoEnabled(False)`——文档不再私藏撤销历史，三层栈**收敛为 canvas 命令栈一层**；文档编辑照常渲染（实时预览不受影响），只是不再产生隐藏的 undo 块。
- 每条命令 = **前后内容快照**（全文 + 必要的逐字符格式），undo/redo = 内容重放；`ui/textedit_commands.py::sync_text_by_diff` 的 diff 重放机制直接复用。
- 键入命令：按"键入会话"聚合——首键开事务，空闲/失焦/选区变化闭事务（定时器基础设施已在 04feaf8 落地，复用）。
- 格式化手势：预览期间文档随便变，手势结束发一条快照命令；**手势宏、悬开定时器、伪造计步全部失去存在理由，删除**。
- 计账：每条命令恰一个撤销步，`num_pushed_textstep` 语义随之归一（缺陷 ③ 自动消解）。

### 4.1 执行策略与阶段划分

| 阶段 | 内容 | 产出可独立出货 | 与终局的关系 |
| --- | --- | --- | --- |
| 阶段 0 | 行为特征护网（见 4.2） | 是（纯测试） | 终局验收基准 |
| 阶段 1 | 格式化手势提交制（见 4.3） | 是 | 与终局兼容，不会白做 |
| 阶段 2 | 镜像对账重构（见 4.4） | 是 | **仅在停留在"文档栈仍启用"状态时才有意义**；若决定直奔阶段 3 则跳过 |
| 阶段 3 | 单栈化终局（见 4.5） | 是 | 终局 |

两条推进路线：

- **策略 A（稳）**：0 → 1 → 2 → 3，每阶段独立验收出货；
- **策略 B（快，推荐）**：0 → 1 → 3。阶段 2 的排水机制在阶段 3 会被整体废弃，跳过可避免白做；阶段 3 风险由阶段 0 护网与阶段 1 的既有成果兜底。

### 4.2 阶段 0：行为特征护网

把排查用离线复现台固化为 `tests/` 常驻测试（真实 Canvas + TextBlkItem + 面板替身 + 按 `on_push_textitem_undostack`/`on_push_edit_stack` 布线），覆盖第二节全部目标行为：

- 纯 canvas 键入撤销/重做；连续键入聚合为一步；
- 纯面板键入撤销；burst 撤销；
- 格式化手势单步（多块、多中间值）；
- **键入↔格式化交错序列（当前失败，以 xfail 标注，随阶段逐个转正——转正即该阶段的 done 判据）**；
- 撤销/重做后画布与面板文本一致性断言。

现有 `tests/test_format_gesture_undo.py` 锁定的宏行为在阶段 3（宏删除）时按新语义重写，此前保留。

复现台已知坑（写给实现者）：offscreen 下 item 的 `hasFocus()` 需要 `gv.show()` + 事件循环后才成立，否则 `ui/text_engine/item.py::on_content_changed` 的发射门整体跳过（症状：键入不产生任何栈命令）；面板替身必须在挂接信号**之前**完成初始 `setPlainText`，否则初始化同步会触发对账（文本不一致时会真的去改 item 文档）；Qt 信号回调内的 Python 异常会 qFatal 直接终止进程（exit 127、无 traceback），复现台布线务必先行。

### 4.3 阶段 1：格式化手势提交制

不动镜像链路，独立成立：

1. 手势判定沿用现有边界钩子（选区变化/非格式化推送/撤销重做入口/清栈）+ 空闲定时器，但语义从"宏悬开"改为"**事务悬开**"：手势开启时记录各受影响 item 文档的 `availableUndoSteps` 快照；
2. 手势闭合（同样的钩子触发）时统一收口：对每个 item 执行 `doc.undo()` **循环排水**到快照 → 以单一事务（beginEditBlock/endEditBlock）重放终值（一个文档块）→ beginMacro + 每块一条命令 + endMacro **同步完成**；
3. 多选一次手势仍是一个宏 = 一个撤销步；宏不再有悬开窗口（生命周期与手势严格重合），缺陷 ② 的切碎路径消失；
4. 排水期间以 `is_formatting` / `block_change_signal` 现有抑制机制防止排水产生的文档变更反向发射命令。

### 4.4 阶段 2：镜像对账重构（策略 B 跳过）

1. `ui/textedit_commands.py::sync_text_by_diff` 去 joint 化：item 侧一律 `beginEditBlock`；
2. `ui/textedit_commands.py::TextEditCommand` 从"各退一块"改为**按步数快照循环排水**（undo 时 `while availableUndoSteps() > snapshot: doc.undo()`，两侧文档各自独立排水）；
3. 面板键入在 pdoc 被 Qt 合并（`new_steps==0`）但内容确实变化时，**仍然产生独立命令**（修"无命令可退"）；
4. 跨命令合并的 burst 用内容重放兜底（复用 diff 重放），redo 侧同理——此处是文档栈方案的复杂度顶点，也是阶段 3 存在的理由。

### 4.5 阶段 3：单栈化终局

1. item/panel 文档 `setUndoRedoEnabled(False)` 全面切换（含切页、批量重渲、粘贴、合并等所有文档写入路径的回归排查）；
2. 全部文本类命令快照化：`TextItemEditCommand` / `TextEditCommand` 改为持前后全文快照（+格式化命令沿用 `old_ffmt_values`/`new_ffmt_values` 值快照模式），undo/redo = 重放；
3. 删除文档步排水、`old_undo_steps` 步数记账、`joint_previous` 语义；
4. IME：预编辑期间本就不产生提交，提交后走常规命令路径，需实测验证。

### 4.6 删除清单（重构完成时应消失的机制）

- `ui/canvas.py` 的 `_format_gesture_timer` 悬开兜底与宏生命周期管理（被同步宏或快照命令取代）；
- `on_propagate_textitem_edit` / `on_propagate_transwidget_edit` 的伪造计步（`push_text_command(command=None)`）；
- `num_pushed_textstep` 的旧双轨约定（缺陷 ③）；
- `sync_text_by_diff` 的 `join_previous` 参数链（`joint_previous` 全链路）；
- `old_undo_steps` / `updateUndoSteps` 步数记账（阶段 3）。

## 五、回退路径与中止判据

1. **分阶段原子提交**：每阶段一个提交，用户审查后入库；任一阶段可用 `git revert` 单独回退，不牵连其他阶段。
2. **中止判据**：某阶段完成后，护网测试或实机验收出现无法在一个工作日内定位的回归 → revert 该阶段；若退到阶段 1 后体系仍不稳定 → 停止方向乙，落地方向甲（甲-1/2/3 与乙不冲突，可先行落地作为底线）。
3. **双向兼容**：甲-1/甲-2/甲-3 是纯局部修复，即使最终走乙也可先合入止血；甲-4 在乙启动后不再单独做（其标记机制会被乙的镜像重构覆盖）。
4. 阶段 0 护网测试同时是回退后的回归保护。

## 六、验证策略

- 每阶段：`scripts/verify.py` 全绿 + 护网测试全绿 + 实机验收清单；
- 实机验收场景清单：纯键入 / 连续键入一步回退 / 中文 IME 输入 / 键入与格式化交错 / 多选格式化一次回退 / 改字号实时预览手感 / 撤销后重做 / 撤销后画布与面板一致性 / 切页与批量重渲后的僵尸命令静默失效 / 批量替换回滚不受影响 / 富文本（注解、着重号、分行格式）块上的全部场景；
- 富文本注意：内容快照必须是**全文 rich text 级**（逐字符格式），不能只存 FontFormat 标量。

---

## 七、风险清单

1. `setUndoRedoEnabled(False)` 与 IME 预编辑、注解 ruby 容器、效果栈渲染的相互作用需实测（阶段 3 首项即验证）；
2. 快照内存：每命令存前后全文，文本块体量小，评估可接受；必要时加命令数上限（LRU 淘汰最旧步）；
3. 排水循环（阶段 1/2）依赖"栈顶往下连续是本手势步骤"的假设，需防御性断言（快照不可达时报错降级而非死循环）；
4. 本体系为 fork 私有重构，与上游撤销实现分道，后续反向移植不再覆盖撤销域；
5. `ui/text_engine/` 存在休眠拷贝，重构只动活代码，休眠拷贝内的同符号不作为参考。

---

## 八、明确不做

- 不把批量替换快照回滚并入本体系（分治已定，见查找替换重构记录）；
- 不做撤销历史的跨页/跨会话持久化；
- 不改绘制栈（draw_undo_stack）；
- 不在本计划内处理上游同步（backport 规范不适用于本域）。
