## 一、竖排标点符号对齐控制

### 概述

全局选项，控制竖排文本中标点符号（`，。、·` 等）在字符格内的对齐方式。此前标点始终硬编码为居中，现支持**居中**和**右上**两种模式，以适配东亚竖排排版标准。

默认值为 `Center`（向后兼容），`PunctuationAlignment` 枚举设在 `FontFormat` 数据类中，自动获得全局默认 + 样式预设双重能力。

### 改动文件

| 文件 | 改动 |
|------|------|
| `utils/fontformat.py` | 新增 `PunctuationAlignment` 枚举（Center/UpperRight）；`FontFormat` 新增字段 |
| `ui/scene_textlayout.py` | `updateDrawOffsets()` 中条件判断取代硬编码居中；新增 `setPunctuationAlignment()` |
| `ui/fontformat_commands.py` | 新增 `ffmt_change_punctuation_alignment` 命令（被 funcmaps 自动发现） |
| `ui/textitem.py` | `TextBlkItem` 新增 `setPunctuationAlignment()` |
| `ui/text_advanced_format.py` | `TextAdvancedFormatPanel` 新增下拉框控件 |

### 实现要点

- 仅影响竖排模式（偏移逻辑仅在 `VerticalTextDocumentLayout.updateDrawOffsets()` 中）
- 右上对齐将 x 从居中 `(line_width - act_rect[2]) / 2` 改为右对齐 `(line_width - act_rect[2])`，y 保持顶部对齐
- 当前受控标点集合：`{'。', '．', '，', '、', '·'}`
- 使用 `IntEnum` 预留扩展空间（如未来添加"左上"等模式）
- 默认 `Center(0)` 与改动前行为完全一致，旧配置/样式预设自动获得默认值

## 二、縦中横（竖内横排）

功能已实现并通过像素验证。

### 需求

竖排文本框中，连续的 `[A-Za-z0-9]` run 在长度 ≤ 阈值时正立横排显示（縦中横），超阈值回退到现有逐字 90° 旋转。用户可配置。

### 设计决策

| 决策项 | 选定方案 | 理由 |
|---|---|---|
| **渲染语义** | C 方案：run 正立自然宽，允许向邻列方向轻微溢出 | 用户选择，贴近漫画印刷风格 |
| **阈值回退** | 位数上限回退：run 长度 > 阈值时整个 run 以逐字旋转回退 | 长 run 横排会严重挤占邻列 |
| **作用范围** | 全局（`ProgramConfig.tatechuyoko_threshold`） | 同类作品风格统一，per-block 交互复杂度收益不成比例 |
| **字符范围** | 仅 `[A-Za-z0-9]` 合并为 run；标点不并入 | 用户确认 |
| **默认值** | 3 | 用户确认 |
| **配置方式** | 面板滑块 0–5，0=禁用 | 用户确认 |

### 改动文件清单

| 文件 | 改动 |
|---|---|
| `utils/config.py` | `ProgramConfig` 新增 `tatechuyoko_threshold: int = 3` |
| `ui/configpanel.py` | "标点对齐"下方新增 `PaintQSlider` 滑块（区间 0–5）+ `on_tatechuyoko_threshold_changed` + `_apply_tatechuyoko_settings`（遍历所有 `TextBlkItem` 应用） |
| `ui/scene_textlayout.py` | `SceneTextLayout`/`VerticalTextDocumentLayout`/`HorizontalTextDocumentLayout` 构造新增 `tatechuyoko_threshold` 参数；`find_tatechuyoko_runs()` 预扫描函数；`layoutBlock()` run 分流逻辑；`updateDrawOffsets`/`draw` 中 `PUNSET_VERNEEDROTATE` 守卫跳过 run |
| `ui/textitem.py` | 4 处 layout 构造调用追加 `tatechuyoko_threshold=pcfg.tatechuyoko_threshold` |

### 实现要点

#### 游程扫描（`find_tatechuyoko_runs`）
- `re.compile(r"[A-Za-z0-9]+")` 匹配连续字母数字段
- 仅收录长度 ≤ threshold 的段；threshold ≤ 0 返回空 dict

#### layoutBlock 分流
- `tl.beginLayout()` 后调用 `find_tatechuyoko_runs` 预扫描 `blk_text`
- 主循环中，若当前 `char_idx` 命中 run：调 `line.setNumColumns(run_len)` 让 Qt 打包整段
- Qt 不接受（`line.textLength() != run_len`）则回退逐字旋转
- run 的 `tbr_h` = `cfmt.tbr.height()`（1 字高，非 `naturalTextWidth`），正立不旋转
- `char_records[run_start]` 记录 `{"line_width": run_naturalTextWidth, "tatechuyoko": True}`
- 列宽仍按单字 `cfmt.tbr.width()` 计算（溢出不占新列）
- `char_yoffset_lst` 按 1 字高生成单对 `[top, bottom]`（与现有 `…`/`—` 多字分支结构一致）

#### 绘制分流
- `updateDrawOffsets` / `draw`：`PUNSET_VERNEEDROTATE` 分支增加 `and not tatechuyoko_rec.get("tatechuyoko")` 守卫
- tate-chuyoko run 走正立 `else` 分支，`line_width` 用 run 宽，在列中心居中
- `line_draw` 传 `line_width=run_w`，使 selected 裁剪矩形用 run 宽而非单字宽

#### 配置面板刷新
- `_apply_tatechuyoko_settings`：遍历 canvas 中所有 `TextBlkItem`，检查 `hasattr(layout, "tatechuyoko_threshold")` 保护，同步 `layout.tatechuyoko_threshold` 后调 `layout.reLayout()` + `repaint_background()` + `update()`
- 通过现有 `ConfigPanel.hideEvent` 触发保存落盘

### 像素验证数据

测试文本 `"あABい"`（24pt，列宽约 200px）：

**阈值 0（逐字旋转）：** 纵轴有墨范围
- (0–28) = `あ`
- (35–56) = `A`（侧倒，占 ~21px）
- (66–81) = `B`（侧倒，占 ~15px）
- (90–112) = `い`
- 总高 **112px**，4 个纵带 = 4 个字位

**阈值 3（縦中横）：** 纵轴有墨范围
- (0–28) = `あ`
- (35–56) = `AB` 整段横排（同一个纵带，~21px = 1 字高）
- (61–95) = `い`
- 总高 **95px**（比 off 短 17px），3 个纵带 = 3 个字位

`AB` run 不再分裂成两个旋转字符的独立纵带，而是合为一个横排组只占 1 字高，后续列位置相应上移。✓

### 实现思路详解

#### 核心难点：竖排布局里如何让一小段横排"挤进"一列

竖排布局由 `VerticalTextDocumentLayout.layoutBlock` 驱动，本质是逐字符往一条竖列里填，列宽按单字 `cfmt.tbr.width()` 计算，字符超出 `available_height` 才换列。QTextLine 在这个布局里被当 1 字的纵带使用。

縦中横要打破的是"一 line 一字"的约定：让一段连续字母数字共享**一条** QTextLine，正立、并排、横排，只占 1 字高、宽度则可能超过 1 字宽。`QTextLine.setNumColumns(run_len)` 是让 Qt 把整段 run 打包成一条 line 的关键调用。Qt 不保证接受（行宽余量不足会回退），所以分流后要校验 `line.textLength() == run_len`，不等就退回 `setNumColumns(1)` 走逐字旋转老路——这是"阈值回退"之外的第二道回退保底。

#### 两套并行索引：QTextLine vs char_records

实现里存在两套对同一个字符的索引方式，理清楚就不易改错：

- **QTextLine 视角**：一条 run 共享一条 line，`line.textLength() == run_len`，`line.naturalTextWidth() == run 横宽`。`updateDrawOffsets`/`draw` 按 `layout.lineAt(ii)` 遍历，每条 line 取一个 `char_idx = line_pos + num_lspaces`（即 line 起点字符）。run 那条 line 的 char_idx 就是 run 起点；run 中段字符不会被单独遍历（它们在同一条 line 里）。
- **char_records 视角**：以 char_idx 为键的 dict。run 起点记录 `{"line_width": run_naturalTextWidth, "tatechuyoko": True}`；普通字符记录 `{"line_width": 列宽}`。

`draw`/`updateDrawOffsets` 通过 `char_records.get(char_idx).get("tatechuyoko")` 决定该 line 走正立横排 `else` 分支还是逐字旋转分支。因此**run 起点 char_idx 上能否稳定保住 tatechuyoko 标志，是整个功能正确性的总开关**。

#### 关键设计抉择与推理

| 抉择 | 选项 | 选定 | 推理 |
|---|---|---|---|
| run 的纵向高度 | 用 `naturalTextWidth`（横宽当高） | 用 `tbr.height()`（1 字高） | run 正立不旋转，纵向占 1 字高，与普通字符一致。横宽只在水平居中时用 |
| run 的列宽 | 按实际横宽占新列位 | 仍按单字宽 | C 方案允许向邻列轻微溢出；列宽按单字算才能让后续字符位置不乱跳 |
| 标志写入时机 | flush 时按 pending 还原 | 分流成功即写 | pending 的单变量延迟还原会在多 run 时覆盖丢失、不换列短文本会在循环末尾 pending=None 前根本不还原；立即写最稳，flush 加守卫跳过已带标志字符即可 |
| 横排居中基准 | 把 run 第一个字居中到列 | 把整段 run 中点对齐列中点 | line.draw 画整条 line，起笔按"第一个字居中"算 = 只锚定首字、其余字符随起笔右延，run 越长越右探。正确做法用 run 总宽 `line_width` 做对称居中：`xoff = (列宽 - run宽)/2 - act_rect[0]` |
| 选中裁剪矩形宽 | 用列宽 | 用 run 宽 | 选中需覆盖整个 run，`line_draw` 的 `line_width` 参数保持 run 宽，居中的视觉基准与选中矩形各走各的值 |

#### 为什么不让超阈值 run 也横排

阈值位数上限回退（run 长度 > 阈值 → 整段逐字旋转）是为了限制"溢出量"。run 横宽 = len × 单字宽，防守溢出最简单是直接限制 run 在列内的长度上限。逐字旋转回退后每个字符独占一格纵带，与无该功能时行为一致，副作用最小。

#### 为什么阈值全局而非 per-block

per-block 要存每个块的阈值并新增交互（右键/属性面板），收益（一页内不同块想用不同风格）极少见、成本不成比例。同作品风格统一是常态，故落 `ProgramConfig.tatechuyoko_threshold` 全局。配置面板改动时 `_apply_tatechuyoko_settings` 遍历所有 TextBlkItem 同步 `layout.tatechuyoko_threshold` + `reLayout()` 实现即时刷新。

### 遗留项 / 已知边界

1. **选中态（selection）**：run 整段是 1 条 `QTextLine`，选中判定只看 line 起点字符是否在选区内。若用户从 run 中段往后选中，起点不在选区内 → `selected=False` → 该段按非选中绘制。这是 run 整段化后的语义简化，与现有 `…`/`—` 多字 line 行为一致。
2. **光标（cursor）**：run 内点击定位到 run 整体，非字符级精度。复用现有 `line.textLength() != 1` 多字二分分支。
3. **横向溢出**：C 方案允许 run 向邻列溢出 `(run_w - col_w)/2`。阈值 ≤3 限制溢出量。可能撞邻列文字。
4. **`draw_shifted`**：`layoutBlock` 中 `if num_lspaces == 0` 的分支 (`shifted = ntw - cfmt.br.width()`) 对 run 会产生大 `draw_shifted`，可能使竖排块边界异常左移。实测中 `_big_on` 列数减少，块缩小方向正确，但需在真实漫画页中验证重叠情况。

### 3.1 PR 概述

该 PR 为 Advanced Text Format 流程添加了四个独立的文字变换维度：

| 变换 | 范围 | 说明 |
|------|------|------|
| **Horizontal Scale** | 10%–400% | 水平独立缩放 |
| **Vertical Scale** | 10%–400% | 垂直独立缩放 |
| **Box Slant** | -85°–85° | 整个文本框剪切（含选择框和手柄跟随） |
| **Glyph Slant** | -45°–45° | 仅字形轮廓倾斜，不改变行布局/换行 |

中性值 `100% / 100% / 0° / 0°` 保持现有渲染路径不变。旧项目加载时自动回退为中性值。

**改动规模**：15 个文件，新增 2 个文件（~1200 行），净改动 ~5800 行。

**4 个 commits：**
1. `5fcbcd55` — feat(text): add independent scale and slant transforms
2. `a62964b1` — refactor(text): simplify transform implementation
3. `139881c6` — refactor(text): deduplicate transform state handling
4. `8cefa80b` — refactor(text): simplify transform controls and move snapshots

### 3.2 文件级分析

#### 新增文件

##### 1. `text_glyph_renderer.py`（+1026 行）

独立字形倾斜渲染引擎。最核心的新文件。

**设计原则**：
- **只读架构**：读取 QTextLayout 已排好的 glyph runs，不修改文档内容

### 3.3 架构亮点（可学习点）

#### 1. 分层清晰

```
FontFormat（数据层：存储 → JSON 持久化）
  ↑
TextTransform（纯数值四元组 + 标准化）
  ↑
text_transform.py（仿射矩阵计算：Box 变换 + 旋转补偿）
  ↑
text_glyph_renderer.py（Glyph Slant 渲染引擎：路径级 + 栅格回退）
  ↑
textitem.py（整合：变换安装 + 效果缓存 + 预览系统）
  ↑
text_advanced_format.py（UI 控件层）
```

#### 2. 旋转补偿矩阵

Qt 的 `QGraphicsItem.rotation()` 总是先于 `setTransform()` 应用。作者用 `C = R⁻¹ × S × R` 作为基础变换，使 `R × C == S × R`（先缩放/剪切再旋转），让已有旋转的文字项也能使用四个新变换。

#### 3. 预览系统

拖拽滑块时实时预览（`_text_transform_preview`），不写入 undo stack。鼠标释放才 commit 生成一个原子 undo 命令。避免拖拽过程产生海量 undo 记录。

#### 4. 批量更新合并

`_text_transform_update_depth` 计数器 + `_flush_text_transform_update()` 合并嵌套调用为一次重绘。

#### 5. 多边形 shape control

将 shape control 从矩形模型升级为通用多边形模型，使 Box Slant 后的平行四边形选择和缩放手柄仍能正确贴边。

#### 6. 字形倾斜与文档隔离

Glyph Slant 完全是渲染层变换，不改变 QTextDocument 的布局计算，因此不影响文本编辑（IME 输入、方向切换、undo/redo）的逻辑。

#### 7. 回退方案完善

对彩色字体（emoji 等无法提取矢量路径的字形），用 QImage 栅格化 + 仿射变换再合成，而非直接放弃。

#### 8. 项目加载的版本迁移

`TEXT_TRANSFORM_SCHEMA_VERSION` + `migrate_text_transform_payload()` 确保旧项目无缝升级，新字段不存在时自动回退中性值。

### 3.5 需要注意的地方

1. **代码量大**（~5800 行净改动），实装前应增量进行，分阶段验证
2. **上游的 text_advanced_format.py** 控件体系与我们的打包控件不同，UI 部分应直接重写而非搬运
3. **shape control** 我们当前实现和上游差异大，多边形化是最复杂的环节，需要先深入理解现有代码
4. **效果缓存系统**（shadow/stroke）的 transform 边界预留需要仔细处理
5. **旋转补偿矩阵**的数学推导要验证正确性，避免因 Qt 版本差异导致矩阵计算错误
