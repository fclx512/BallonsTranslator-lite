# 模型说明卡片 规划

> 状态：规划草案（2026-09-19）。UI 部分暂不定稿，本文只定内容结构、数据存放与分期计划。缘起：接入 paddle-ocr-for-manga（见 `docs/技术实现/paddle-ocr-for-manga_接入调研.md`）时暴露的问题——各阶段可选模型各有定位与门槛，用户选型时没有任何提示，只能靠名字猜。

## 1. 目标

- 管线四个阶段（文字检测 / OCR / 翻译 / 图像修复）的**每个可选模块**配一张「说明卡片」，回答三个问题：它擅长什么、跑起来要什么、什么时候该用它。
- 卡片内容聚焦**选型**，不重复参数说明：参数含义仍然只在各模块 params 的 description 里（配置面板已有）。
- 本分支精简导向：卡片是纯静态文案 + 简单展示位，不做评分、不做在线内容、不引入新依赖。

## 2. 范围

- 在范围内：四阶段注册表中所有模块，含 `none` 系（一张「跳过此阶段」的说明卡，讲清没有模型的后果），含规划中的新模块（如 paddleocr_vl_manga）。
- 不在范围内：文字渲染（内置引擎，无可选模型）；LLM Profile 本身（「模型管理」页已有自己的说明体系）。
- 一类特例要在卡片里讲清楚：**跨阶段模型**。PaddleOCR-VL 系天然横跨「版面/检测 + 识别」，本项目只取其识别半边、检测继续用自己的检测器；卡片负责说明这类「模型能做什么 vs 本项目用它做什么」的取舍。

## 3. 卡片字段（统一 schema，草）

| 字段 | 说明 | 示例（paddleocr_vl_manga） |
| --- | --- | --- |
| 定位 | 一句话：这是什么、强在哪 | 日文漫画专精的生成式 OCR，质量最高 |
| 特点 | 按阶段措辞：识别特点 / 检测特点 / 修复效果 / 翻译风格 | 整块识别、自带阅读顺序；竖排友好；全半角/部首变体是已知误差类型 |
| 门槛 | 设备、显存、额外依赖、付费/外发 | GPU-only（约 3GB 显存）；需 CUDA 版 torch + transformers；权重 1.9GB |
| 适配注意 | 本项目接入的要点与坑 | 识别-only，检测器不变；逐块生成慢（估 10~60s/页）；无置信度分数 |
| 适用 | 推荐场景 / 不推荐场景 | 高质量日漫精翻；不适合批量快跑或非日语 |

字段数固定为 5，全部必填、每条 1~2 行。来源/许可不单列（写进「门槛」或「定位」，避免卡片膨胀）。

## 4. 数据存放与 i18n（推荐方案）

- **集中一张静态数据表**（新建单文件，如 ui/model_cards.py，键＝注册名），不放各模块文件里：
  - 模块注册是懒加载 AST 扫描（utils/lazy_registry.py），**不导入模块体**；集中表零导入开销，也让卡片独立于「模块能否成功 import」。
  - 新增模块时改一处即可；分散在 15+ 个模块文件里反而容易漏。
- 文案 i18n：在字面量定义处用 QCoreApplication.translate 显式标注上下文（同 ui/configpanel.py::_ACTION_NAMES 先例），下游直接取已翻译值；遵循仓库 i18n 规范（严禁 self.tr(variable) 间接查表）。
- **不复用**模块 params 里的 description：那是英文单行、面向参数表单的，与面向选型的中文长文案是两回事；混用会互相污染。提取链（scripts/i18n_common.py::extract_param_descriptions）也不动。
- 备选（暂不做）：模块文件内自描述 `MODULE_CARD` + AST 提取。等卡片字段稳定且确有「随模块走」的需求再评估。

## 5. UI 落点草案（不定稿）

三个候选落点，按优先级：

1. **配置面板 Pipeline 页**（ui/configpanel.py::_build_pipeline_page）：页内已按阶段分块、只展示当前引擎参数——在阶段分块的引擎选择处旁挂当前模块的卡片，最贴合「先看说明再调参」。形态：GroupFrame 容器 + 标题行，正文纯文本五字段，无图。
2. **运行对话框**（ui/run_pipeline_dialog.py）：启用模块网格 + 模块下拉处，选中模块即在折叠区顶部显示同一张卡（复用同一数据源与控件）。
3. **底部栏模块选择器**：hover tooltip 显示「定位」一行，成本最低，作为兜底顺带做。

统一约束：卡片控件做一个可复用小组件放 ui/custom_widget/，三处共用一个数据源；文案超长可滚动，不做弹出大窗。示例图（修复前后对比、检测效果）**后期可选**，P1/P2 不做。

## 6. 现有模块清单与卡片种子内容（P1 素材初稿，实现时逐个核对）

> **2026-09-19 模型精简决策**：`ctd`／`mit48px_ctc`／`aot`／`Sakura` 四个模块删除（与保留模块定位重叠，用户长期实测属「不好不坏」档；Sakura 的单框无上下文翻译与 LLM 全局剧情概览流程冲突），已登记 `scripts/audit_registry.json`。`patchmatch` 保留注册但**不进选型界面**（`modules/__init__.py::HIDDEN_INPAINTERS`）——它只适合涂简单背景，不藏会被不懂的用户当常规修复模型选用；卡片清单不含它。精简后四阶段结构＝「默认主力 + 轻量/兜底 + LLM 档」。

以下为基于仓库现状写的初稿，正式内容在 P1 按字段模板补全。

**文字检测**

| 注册名 | 定位（初稿） | 门槛要点 |
| --- | --- | --- |
| ysgyolo | YSG-YOLO，当前默认；带文字区类型分类（气泡/旁白/拟声等），漫画版面友好 | ultralytics 路线，GPU 更佳；权重走 HF 下载 |
| ppocrv6_onnx | PP-OCRv6 DBNet（onnxocr，无 paddle 依赖）；文档系通用检测，支持 rtl 阅读顺序；区域再检测的默认检测器 | onnx，CPU 可跑，速度快 |
| none | 跳过检测：只对已存在的块做后续流程 | 无模型 |

**OCR**

| 注册名 | 定位（初稿） | 门槛要点 |
| --- | --- | --- |
| paddleocr_v6_onnx | PP-OCRv6 识别-only（onnx），多语种快；「OCR 置信度低」自动挂标仅此链路生效 | onnx；GPU 需 CUDA 版 onnxruntime-gpu |
| llm_ocr | vision LLM 整图/整块识别，疑难图兜底 | 需 vision profile；慢、按量付费、图像外发 |
| none_ocr | 跳过识别：保留已有原文直接翻译 | 无模型 |
| paddleocr_vl_manga（规划中） | 日漫生成式 OCR，质量优先 | GPU-only，见接入调研文档 |

**翻译**

| LLM_Agent_Translator | agent 多轮 + 只读探索工具，复杂页质量优先 | 需 profile；token 消耗高、最慢 |

**图像修复**

| 注册名 | 定位（初稿） | 门槛要点 |
| --- | --- | --- |

| none | 不修复：保留原图/预修复层 | 无模型 |

## 7. 分期计划

- **P1 内容**：建数据表文件 + 按第 3 节字段把上表补全成正式卡片（11 张 + 新模块随接入补充）；跑 i18n 链路出中文。
- **P2 UI**：实现卡片小组件，落点按第 5 节顺序（Pipeline 页 → 运行对话框 → tooltip）；验收＝两处显示一致、跟随语言切换。
- **P3 规范**：在使用说明/AGENTS 补一句「新增管线模块须随附卡片条目」；可选：check 脚本校验「注册表键与卡片键一致」（防新模块漏卡）。

## 8. 与 paddle-ocr-for-manga 的关系

- 该模块接入（`docs/技术实现/paddle-ocr-for-manga_接入调研.md` §4）落地时随附第一张正式卡片，作为本体系的试点样例。
- 它是「跨阶段模型」的典型（检测+识别一体、只用识别），第 2 节的特例说明即以此模型为原型；后续若真有人想用 VL 模型做整页版面，也应先读卡片里的取舍说明再动手。
