## 1. 断言核实结果

规划 §9 的实现层调研整体可信，**未发现方向性错误**——没有哪条决策因断言失真而落不了地。但有以下偏差需要修正认知。

### 1.2 规划未提及但影响落地

1. **LLM OCR 从不挂置信度标签。** `apply_ocr_confidence_tag` 的调用点只有 `modules/ocr/ocr_onnx.py` 与 `modules/ocr/mit48px_ctc.py` 两处；`modules/ocr/ocr_llm_api.py` 不调用。→ 用 LLM OCR 的项目，这类块**永远得不到 `ocr_low_conf` 标签**（注意：`ocr_low_conf` 本就不单独入工作台队列，队列由 D38 的误识别正则标签产生，见规划 D28 的队列口径）。程序筛选器落点选 hook 后正好天然覆盖它（D39）。
2. **`updateTextBlkList` 会用面板值覆盖数据、并把 `blk.text` 折叠成单元素。** `ui/scenetext_manager.py::SceneTextManager` 的该方法在整页重建时以 `trans_pair.e_source` 的整段文本写 `blk.text = [ ... ]`（**不是逐行列表**），同时写回 `blk.rich_text`／`blk.translation`／`blk._bounding_rect`。→ 它会把 D33a 的"逐行展开"冲掉。**这是批量写回必须走 D40 五步顺序、且事后禁止再调它的直接原因。**
3. **`page_data_needs_sync` 的判据只比长度与对象身份、不比内容。** `utils/block_actions.py::page_data_needs_sync` 在"长度不一致"或"`blk is not item.blk`"时返回真；`ui/mainwindow.py::MainWindow` 的 `_sync_block_data` 据此决定是否调 `updateTextBlkList`。→ 数据层换成新块对象后若不同步重建视觉层，**任何后续框级动作都会用旧视觉层整页覆盖新数据**。D40 的可验证判据即由此而来。
4. **`ui/mainwindow.py::MainWindow` 的 `_sync_block_data` 是现成的"动作前数据一致性修复"入口**（AGENTS.md 已登记），可直接作批量操作的前置对齐步骤（D40 第 ① 步）。
5. **`utils/textblock.py::TextBlock` 的 `vertical` 与 `src_is_vertical` 是两个东西**：前者是 `fontformat.vertical` 的可写属性（渲染方向），后者是检测产物（原文方向）。规划的 D32／§6.3 的"竖排"一律指 **`src_is_vertical`**（原文方向）；实现时不要误用 `vertical`。
6. **LeftBar 图标走 QSS，规则共 5 组 × 3 态 = 15 条**（`base`／`:hover`／`:checked`，后两者用 `_activate` 图标），其中 2 组无 `leftbar_` 前缀（`showpagelist.svg`／`search.svg`）。D25 改造 `glossaryChecker` 槽位只改 `QCheckBox#GlossaryChecker` 那 3 条规则的 `url`（连 `objectName` 一起改则 3 条选择器同时改），**不需要新增 QSS 选择器**。另有现成闲置资源：`icons/leftbar_stylemgr.svg` 与 `leftbar_stylemgr_activate.svg` 全仓无代码／QSS 引用。
7. **`utils/block_tags.py::set_tag` 是覆盖写**（`blk.tags[tag_id] = {...}`），而 `remove_tag` 是整条删除。→ D28 的 `reviewed` 必须落在**已存在的条目**上；"驳回"要写成 `set_tag(..., reviewed=True)`，若先 `remove_tag` 就无处存状态。
8. **`ui/context_menu_config.py` 有 `_merge_default_order` 逻辑**：会把 `DEFAULT_ORDER` 里新增、而用户已保存菜单里没有的条目按前驱位置自动补进去。→ 新增标签**会自动出现在老用户的右键菜单里**，不是"必须手动加进 `DEFAULT_ORDER` 才可见"那么绝对（但加进 `DEFAULT_ORDER` 仍是必要的，否则它没有"前驱"可挂靠）。
9. **OCR hook 的遍历位置在 `none_ocr` 分支之外。** `modules/ocr/base.py::OCRBase` 的 `run_ocr` 里钩子是"每个块列表都跑"，而 `none_ocr` 的语义是**保留已有文本**（`blk.text` 不清空）。→ 程序筛选器若不短路 `none_ocr`，会在"用户选择不 OCR"的项目上凭空挂出一批"空文本／纯符号"标签。已写入 D39 的落地要求。

## 2. 复核问题的关闭结论

以下 11 条是复核时暴露的问题，均已关闭；括号内为结论所在的规划条目。

1. **D18 的"撤销占用上限"设置项是否还需要？** → **不新增，沿用现有步数上限**（规划 D18）。`utils/config.py::ProgramConfig` 的 `undo_steps_limit` 即内存侧唯一约束。D21 的"批量一律落盘"保留（用户自评方向"稍许激进"、前提"可接受写盘"成立，实测后再议）。
2. **误识别类正则标签是 4 个独立 id，还是 1 个 id + 子类型字段？** → **1 个独立标签 + 条目内子类型字段**（规划 D38）。四类判定（空文本／纯数字／纯符号／无假名汉字）作为条目内字段、允许一个块命中多类；驳回粒度为**块级**。**配套**：`utils/block_tags.py::TagDef` 需新增"程序专用、不进人工打标途径"的声明（现有 `source` 字段不是此判据）。
3. **`reviewed` 承载几种取值、驳回是否可逆？** → **布尔、可逆、不从队列消失**（规划 D28）。驳回后卡片保留、只覆盖"已驳回"遮罩，再次点击即取消；驳回条目不计数但仍可见、可再点取消——不引入第三态。**驳回为块级**（同时作用于该块全部程序标签条目）；**队列口径**＝带 D38 误识别正则标签的块（按块去重），`ocr_low_conf` 不单独入队（见规划 D28）。
4. **队列里"已勾选待删除"是否持久化？** → **不持久化（会话内界面态）**（规划 D27）。理由：勾选是"本批次待执行意图"，执行即消失；落盘会留下无法区分"忘了取消"与"确实想删"的残留态。驳回与勾选**两轴正交、互不自动联动**。队列状态模型定稿：持久侧只有 `reviewed`；**不存在"已确认通过"态，未驳回即待处理**。
5. **程序筛选器落点二选一。** → **走 OCR postprocess hook**（规划 D39）。机制现成、对 `OCRBase` 注册一次即覆盖全部 OCR 模块（含零标签的 LLM OCR）、零遍历代码；代价是要处理 `none_ocr` 短路（见 §1.2 第 9 条）。
6. **D15 的"程序标签徽标默认不显示"怎么落地？** → **不影响画布**。D15 只约束**工作台审批界面的呈现**（整合／精简显示），`utils/config.py::ProgramConfig` 的 `show_tag_badge` 与画布徽标行为**完全不变** —— `ui/textitem.py::TextBlkItem` 的 `refresh_tag_badge` 无需改动，**`reviewed` 也不参与此处的徽标过滤**（驳回只在工作台界面以遮罩呈现）。
7. **是否顺手修 `sort_regions`？** → **不修，只自建**（规划 D41）。它被 `modules/textdetector/detector_paddlev6.py` 与 `modules/textdetector/detector_ysg.py` 调用，改动即变更**所有检测器**的初始输出顺序、需全书回归，与本次目标无关；方向判定本就在组级自建（D32）。缺陷就地登记，留待后续单独处理。
8. **批量合并的 `rich_text` 与 `lines` 怎么处理？** → **三者必须同序一致**（规划 D40 契约一／二）。`rich_text` 必须重建（渲染实际消费它，留旧值会导致渲染与数据不一致）；`lines` 与 `text` 逐个对应；"反转该组方向"按钮同时改三者。**形态澄清**：`utils/textblock.py::TextBlock` 的 `get_text()` 是**空串拼接**（仅字母边界补空格、不插换行），故"逐行展开／按块分段"的差异体现在**列表结构与导出、编辑框**上，不在渲染。
9. **批量操作写回顺序与 `updateTextBlkList` 的冲突怎么防？** → **D40 的五步顺序 + 可验证判据**。① `_sync_block_data` 前置对齐 → ② 只改 `proj.pages` → ③ `bump_page_generation`（动图像时加 `bump_page_image_generation`）→ ④ 当前页 `updateSceneTextitems` 重建视觉层 → ⑤ **此后禁止**再调 `updateTextBlkList`。判据：完成后 `page_data_needs_sync(current_block_list(), textblk_item_list)` 必须为 **False**。非当前页不重建 UI（切页时自然走 ④）。
10. **D33d 的误聚阈值默认值取多少？** → **85% 定稿**（规划 D33d）。用 §6.3 同口径复算样本（435 组，数字与规划完全吻合：中位 83×148、p90 宽 200、最大 1827）：≥85% **仅命中 2 组（0.5%）**——`093.jpg` 903×117／页 1015×1457＝89%（2 成员）与 `057.jpg` 1827×208／页 2063×1457＝89%（10 成员），形态均为**跨栏气泡**；且阈值不敏感（≥50% 4 组、≥60%~70% 3 组、≥80%~85% 2 组、≥90% 0 组），无需精细校准。行为规则（默认不勾选 + 警示标 + 设置内可调）不变。
11. **D24 的工作台目标宽度取多少？** → **默认维持 `WORKBENCH_WIDTH = 460`**（规划 D24）。依据：合并组图 p90 为 200×208 px，加 D31 外扩（短边 50% ≈ 40 px）后约 280×288 px，在 460 内可 100% 全幅显示、无需滚动；仅 2 个跨栏大组（最大 1827 px）需滚动，而它们本就默认不勾选。实现后若实测不足只改该常量（面板内部宽度自适应，零布局改动）。

**依赖关系**：A → D（队列数据来源）；B → C1/C2/C4（批量撤销载体）；A → C2（D30 的排除判据）；C2 → C3 的顺序（D16／§6.4）；C 组与 D 组可并行。规划 D37 已明确**不强制步骤顺序**，运行时只做跳步提示。

**建议的先行验证**：A 组内先只做"标签 + `reviewed` + 挂标 + 队列查询"，用现有样本跑一遍确认队列规模（规划 §7 预估约 128 条 / 平均每页 1.4 条）是否与实测吻合，再决定队列 UI 的信息密度——这比先搭 UI 再发现数据形态不对要省。

**C1 的验收复算流程（判据命中率，2026-09-16 登记）**：C1 已按"只涂判据取假的简单块"的保守口径落地。施工区样本实测命中率**只有 8.3%**（1565 框：简单 130 ／复杂 90 ／**判不出 1345**），根因是判据（`modules/inpaint/base.py::classify_simple`）要求裁剪区内存在**一条盖住全部遮罩像素的闭合气泡轮廓**，而样本的框是**逐行框**——1.7 倍裁剪里没有气泡轮廓，放大裁剪也无用（邻框文字进了同一裁剪区，判据的"一条轮廓盖住全部文字"更难满足）。故命中率与**框的粒度**绑定，验收时按下列流程复算：

1. 在实机项目里**把同一气泡内的文本框合并**（手动合并或 C2 批量合并）并清理误识别框；
2. 对更新后的项目 JSON 跑**只读**复算：`proj = utils/proj_imgtrans.py::ProjImgTrans(directory=项目目录)` → `plan = ui/batch_inpaint.py::BatchSimpleInpaint(proj, None).plan()`，读 `plan["simple"] / ["complex"] / ["unknown"] / ["page_count"]`。`plan()` 纯只读（可用文件 mtime 自证）、不需要修复模型与 GPU，全书页约 2 s；
3. 判读：合并后框变"气泡级"，`unknown` 应大幅下降、`simple` 上升。若仍不理想，再在"判据改用**块局部遮罩**（只保留本框内的遮罩像素）"与"换用手动框选那套判据（`utils/textblock_mask.py::canny_flood`）"之间定夺——两者的样本数字与代价见 C1 的功能描述文档（块局部遮罩实测 39%；换手动判据实测 90%，但它不找气泡、只看裁剪区平不平，会把压在复杂背景上的字一起涂掉）。

**实现层自由度**：不影响功能语义的实现选择由施工层自行决定——例如标签 `id` 命名与子类型字段名、设置项 key 命名、几何聚类与方向判定的具体算法形式、UI 控件选型与样式细节、备份文件的目录名。**以下不算自由度、必须遵守**：① 新增标签类型须同步 `utils/block_tags.py::TAG_DEFS`、`ui/context_menu_config.py::DEFAULT_ORDER`、`translate/zh_CN.ts`、`tests/test_tag_toolbar.py` 四处；② 批量写回须按 D40 五步顺序、并满足"完成后 `page_data_needs_sync` 为假"；③ 审批截图须 100% 原始比例（D11）；④ 所有批量行为须弹窗告知（D27）。
