# 区域再检测：设计与实现

> 人工在画布上拉一个矩形 → **只在该矩形内**跑一次「文本检测 + OCR」→ 检出的新块
> 并入本页数据。等于用第二个检测器的精细度补第一检测器的漏检，同时把它"到处拉框"
> 的敏感性限制在人手指定的区域里。
>
> 本文是唯一的设计依据（原方案草稿在 `tmp/`，会随临时目录清理）。实现落点：
> `ui/region_redetect.py`（任务层）、`ui/region_redetect_tool.py`（UI 层）。

---

## 1. 为什么做（背景与实测）

实际工作流是 **ysgyolo 检测 + paddleocr_v6 识别**。ysgyolo 干净，但会成片漏检
**横排文本**（标题、旁白、手机屏内的字）：实测漏检率 **横排 20.5% vs 竖排 7.7%**，
全书约 47 个框、20 页。而**全量双跑复核没有油水**（两模型一致率 88%~92%），
所以只能"人工指定区域"。

**机制（别搞反）**：`ppocrv6_onnx` 的参数是 `det_limit_side_len=960` /
`limit_type='max'`，而 `ballontrans_pylibs_win/Lib/site-packages/onnxocr/operators.py`
的 `DetResizeForTest` **max 模式只缩小、不放大** → 全页 1032×1457 被压到 **0.659×**，
裁剪图按原尺寸送检 ⇒ **同一个模型在小裁剪里的字，等效比全页大 1.5 倍**。
这才是"小区域更精细"的真正原因。

**实测**（外扩 24px → 裁剪 → 只收区域内）：

| 区域 | 区域内 ppocrv6 | 同裁剪 ysgyolo |
|---|---|---|
| 063.jpg 手机屏（横排 5 行） | **5 框** | **0** |
| 047.jpeg 底部 3 行旁白 | **3 框** | **0** |
| 047.jpeg 左中 2 行旁白 | **2 框** | 1 |

**主动再放大无收益**：`1×／2×／3×` 三档检出数一个没多（5/5/5、3/3/3）⇒ 设计里
**不提供放大参数**。

## 2. 已拍板的七项设计

| # | 决策 | 落地 |
|---|---|---|
| 1 | 触发方式＝复用拖框手势 + 独立模式位 | 底部栏「区域再检测」开关；打开后**左键**拉框改道（右键保持建框/菜单语义） |
| 2 | 设置里提供「再检测用的检测器」，默认 `ppocrv6_onnx` | `utils/config.py::ProgramConfig` 的 `region_redetect_detector`，与底部栏管线选择器解耦 |
| 3 | 区域外过滤 | **按四边形顶点中心**是否落在用户框内收块（外扩区实测会带进 1~2 个无关框） |
| 4 | 重叠 **>50%** 的已有块**替换**，其余新增 | 分母取**两者较小者**（见 §4.3）；不弹窗，靠"结果可见 + 一步撤销" |
| 5 | 不整页重排，按坐标插入；失误兜底为追加末尾 | 见 §5（三重兜底） |
| 6 | 检测时把裁剪 mask 贴回页级 | `paste_mask`（并集 + 落盘 + 图像代数） |
| 7 | 新块样式继承邻近块/同页块 | 继承同页**最近**块的 `fontformat`；**字号另算**（见 §4.4） |

## 3. 实现结构

```text
画布左键拉框 → ui/canvas.py 的 region_redetect_rect 信号
        ↓
ui/region_redetect_tool.py 的控制器：受理 → 起后台线程
        ↓ 后台线程跑「检测（要建 ONNX 会话）+ OCR」
ui/region_redetect.py::RegionRedetect 产出 plan
        ↓ 主线程
ui/region_redetect_tool.py::RedetectCommand → push 到画布撤销栈
        ↓                              ← 一次拉框 = 一步撤销
ui/region_redetect.py::RegionRedetect 的 apply／paste_mask 写数据层
```

**任务层（`ui/region_redetect.py`，无 Qt widget，工作台可复用）**：

- `ui/region_redetect.py::RegionRedetect` 的 `plan`——**只读**：裁剪（外扩 `RedetectConfig.expand`）→ 检测 →
  坐标回映射 → 区域外过滤 → 替换决策 → `RedetectPlan`；
- `ui/region_redetect.py::RegionRedetect` 的 `build_page`——**纯函数**：把"替换 + 新增"算进页块列表（含插入点），
  不改任何东西，便于单测与离线复算；
- `ui/region_redetect.py::RegionRedetect` 的 `apply`／`paste_mask`——数据层写回。

**UI 层（`ui/region_redetect_tool.py`）**：`ui/region_redetect_tool.py::RedetectCommand`（撤销命令）、
`ui/region_redetect_tool.py::_RedetectWorker`（后台线程）、
`ui/region_redetect_tool.py::RegionRedetectTool`（控制器：接手势、给通知中心进度提示、
拒收管线运行中／已切页的结果）。

### 3.1 与三处"现成设施"的关系（**刻意不复用**的原因）

- **触发入口不是** `ui/image_edit.py::ImageEditMode` 的一个值：`ui/canvas.py::Canvas`
  的 `setPaintMode(False)` 会把它重置成 `NONE`（进文本框编辑页必然被清掉），且绘图
  模式下 `canvas.textLayer` 是隐藏的——检出的框看不见。改用底部栏开关 + 独立的
  `region_redetect_mode` 布尔位。
- **OCR 不走** `ui/module_manager.py` 的 `_blktrans_pipeline`：那条路径收尾会压一条
  `ui/drawing_commands.py::RunBlkTransCommand`，一次拉框就产生**两个撤销步**；
  改为与它同口径直接调 OCR 模块的 `run_ocr`（`modules/ocr/base.py::OCRBase`），
  `utils/block_tags.py::apply_ocr_confidence_tag` 的自动挂标随之内建。
- **不碰** `utils/batch_versions.py`：那是批量的唯一备份口，本功能是单页单手势，
  撤销走画布撤销栈。

## 4. 关键取舍与实测口径

### 4.1 几何判据一律按四边形，不用 `xyxy`

`utils/textblock.py::TextBlock` 的 `xyxy` 只是**轴对齐外接矩形**；检测器返回的是 DB
**四边形**（实测倾斜 11.9°~16.7°，`angle` −4…−12）。用外接矩形做区域过滤与重叠判据
会误判邻居。故 `utils/block_geometry.py` 增设四边形族（`poly_of`／`poly_center`／
`poly_bands`／`poly_overlap_ratio`），与既有的矩形族共用一份实现。

### 4.2 区域外过滤

取块四边形的**顶点均值**（规划 §八.1 的口径，不是形心）作为中心，落在用户框内才收；
被剔除的块计入 `RedetectPlan.dropped_outside`（063 实测剔 1 个、047 剔 2 个）。

### 4.3 替换判据：分母取较小者

`poly_overlap_ratio = 交集面积 / min(新块面积, 旧块面积) > 0.5`。

若按"旧块面积"算，ysgyolo 的**区域级大框**（短边中位 152px，整个气泡）被 ppocrv6 的
逐行小框压住时永远到不了 50%——而那正是最该被替换的一种。取较小者后两个方向都识破：
"新块落在旧块里"与"旧块落在新块里"都算同一片文字被重新检出。

**替换不迁移翻译/样式**（使用场景就是"旧块本身是错的"）。真机复核：063 的
待替换 `[5,6,7,8,9]` 与新块一一对应（同 5 行、文本完全一致）⇒ 判据没误伤，替换幂等；
047 两组各替换掉 1 个把多行包住的旧大框——正是本决策的典型场景。

### 4.4 样式继承 + 字号另算（决策 7 的例外）

继承同页**最近**块的整份 `fontformat`（字体族/颜色/描边/对齐…），但**字号不继承**：
回映射后重跑 `utils/textblock.py::examine_textblk`（它的角度是平移不变量，字号/距离
在页级坐标下才有意义），按实际检出四边形的行高量出字号，并写回 `_detected_font_size`。

理由是这条既有缺陷：`modules/textdetector/detector_paddlev6.py::PPOCRv6Detector` 的
第 5 步 `sz = blk._detected_font_size * fnt_rsz` 会把 `examine_textblk` 刚算好的字号
**覆盖成 −1**（ppocrv6 从不设 `_detected_font_size`）⇒ 新块**从检测器拿不到可用字号**，
继承邻居的字号又只是碰运气；量出来的最准（063 实测 18~20）。

### 4.5 掩码是栈外图像写入

`paste_mask` 用 `np.bitwise_or` 并进页级掩码、写盘、加图像代数——与管线修复阶段的写法
同构（`utils/proj_imgtrans.py::ProjImgTrans` 的 `save_mask` +
`bump_page_image_generation`）。**撤销不回退掩码**：它是派生的像素数据，撤销范围以
"新增 + OCR 文本 + 标签 + 可能的替换删除"为准。

### 4.6 页代数不 bump

`bump_page_generation` 是给**栈外**整体换新页块列表用的；本功能是栈内写入（与
`ui/scenetext_manager.py::DeleteBlkItemsCommand`、`ui/scenetext_manager.py::RearrangeBlksCommand` 同性质），
bump 会把本命令自己的撤销一并僵尸化。未触碰的块保持对象身份，`resolve_blk_entry`
按 blk 锚点照样解析得到；被替换掉的块其锚点解析为 `None`、相关命令安全跳过。

### 4.7 内存策略：**CPU + 用完即卸**（2026-09-17 实测）

改动前一次手势能让 app 从 **600MB 涨到 1700MB 且不回落**。归因（`tmp/_mem_probe.py`）：

| 步骤 | 进程工作集 | GPU（nvidia-smi） |
|---|---|---|
| 基线（配置 + 开项目） | 589 MB | 291 MiB |
| ppocrv6 **CUDA** 首次 `detect` | **1439 MB（+835）** | 692 MiB |
| `unload_model()` + gc | 1391 MB（**只回收 50 MB**） | 434 MiB ✓ |

- 元凶是**给这条路径新建的 ONNX Runtime CUDA 会话**：会话建立 +165MB、首次推理再
  +670MB（cuDNN 卷积 workspace 与 arena）；**GPU 侧卸得掉，主机侧不还**。
- cudnn 搜索模式（EXHAUSTIVE→DEFAULT/HEURISTIC）、`enable_cpu_mem_arena`、
  `arena_extend_strategy` 三个开关都试过，**只把峰值从 835 压到 730，量级不变**
  （`tmp/_mem_probe2.py`）⇒ **"卸模型/清缓存"救不回来**（卸载 ≈0、`empty_cache` ≈0），
  唯一有效的**预防**手段是**别用 CUDA 建它**；**事后**要还只能靠手动释放（卸载模型 →
  销毁 CUDA 上下文 → 交回工作集，实测 1503MB → 111MB，见
  `docs/技术实现/内存释放_设计与实现.md`）。
  （所以设置里的「清除模型缓存」对本工具无效：它只卸管线模块，而且 ORT 的分配器
  已长在进程里。）
- **CPU** 同一裁剪 **+89~134MB** 且卸载可回收；单次推理 CPU 19~93ms vs CUDA 7~21ms
  （`tmp/_mem_probe3b.py`），**一次手势只差约 20ms**，会话重建仅 0.17s。

故：`RedetectConfig.device`（`pcfg.region_redetect_device`）**默认 `cpu`**，且控制器在
每次手势收尾调 `unload_detector`（不把会话留成常驻内存）。修复后复测
（`tmp/_mem_after_fix.py`）：峰值 **+148MB**、卸完相对基线 **+47MB**，单次手势
0.21~0.32s。

> 注：链路里剩下的内存波动来自 **OCR 模块**（`paddleocr_v6_onnx`，管线共用实例，首次
> `run_ocr` 才懒加载其 CUDA 会话）。那是 app 既有行为，不属本功能——用户已跑过管线时
> 不会新增。

## 5. 阅读顺序：整组坐标插入与兜底

**不整页重排**：走 `utils/textblock.py::sort_regions` 重排会打乱用户手工调过的顺序，
而本功能恰恰是在"误识别与顺序都处理好了"之后才由人工触发的。**前提是已有顺序正确**，
插入只需跟着它走。落点算法在 `ui/region_redetect.py` 的
`group_center`／`new_precedes`／`insert_index`：

1. **整组一个落点**：一次手势检出的几个框先算出共同中心（`group_center`＝各块四边形
   中心的均值），整组插到**同一个下标**，组内维持检测器给的阅读顺序。逐个算下标会让
   同片区域的新块散开（实测一个竖直气泡的 2 个框落到第 6 与第 8 位，中间夹着无关旧块），
   而"第一个可插入位置"这种扫描本身也不自洽——插进去一个，后面每个块的相对位置都变了；
2. 从列表头往后扫，找**第一个「新块应排在它前面」**的已有块 → 落点就是它的下标；
3. 单元判据（`new_precedes`）与 `sort_regions` 的插入口径**同源**——已有顺序就是它排的：
   - 新块中心在对方**纵向跨度之下** → 对方在前；
   - 在跨度**之上** → 新块在前；
   - 落在跨度**之内**（同一行）→ 按页方向比 x（`rtl` 时大者在前）。
4. **页方向**（右到左/左到右）不从 `sort_regions` 取，改用**当前页已有块的成对先后
   投票**推断；样本不足时回落到漫画竖排的通行约定（右到左）。**只有同一行的两块才有
   投票资格**（一块中心落在另一块的纵向跨度内）。

**为什么是"先纵向、再横向"**：漫画是**行优先**的（行自上而下、行内右起），跨行的两块
之间比 x 没有意义。初版判据按"主方向带是否重叠"决定比 x 还是比 y，于是跨行的两块也去
比 x，右下角的框因为"比右上角的更靠右"被判成该排在最前面——这正是"新块总往最前面插"
的主因（用户 2026-09-17 在主力机上的观察）。页方向投票同样有这层噪声：初版把每对相邻
块都算进去，8 票里 3 票是跨行噪声，页上少一个块就能把结论从右到左翻成左到右。

**兜底**（任一情况一律**追加到末尾**，语义等同"新增文本框"，用户自行拖）：页上一个参照
块都没有（`RedetectConfig.min_neighbors`＝1）、整组中心取不到、插入点计算抛异常。
依据码见 `ui/region_redetect.py` 的 `INSERT_*`（进报告，便于复算）。

**实测口径**（`projects/004_819b9e93`，三页共 21 个样本：把每个已有框自己当作拉框
区域重检测，看新块是否**连续**落回被替换块原来的下标）：旧判据 5/21，现判据 **21/21**。

**回归台已常驻**：`scripts/region_redetect_order.py`（落点判据是几何启发式，改一次就得
拿真实页面复核一次，合成单测锁不到"这片漫画该怎么读"）。`--detect` 真跑检测并写缓存
`tmp/region_redetect_plans.json`，不带 `--detect` 读缓存**离线**判（秒级），
`--candidates` 打印候选判据对比表——**改判据前先用它确认新方案真的赢过现役**（现役
21/21、逐块各自算 20/21、折线投影 0/21）。用法见 `scripts/README.md`。

**原则：宁可顺序不理想，也不能插错位置把已有顺序搞乱。**

## 7. 边界与后续

- **v1 单区域**（一次拉框＝一个区域）、**不提供"只检测不 OCR"变体**；
- **拉框跨多行时，整组仍落在同一个下标**（§5 的整组语义）：一次手势检出的框被当作
  一片区域，跨行拉框（框住两行气泡）时新块会挤在同一处、而不是各自回到所在行。
  这是"整组"换来的确定性，真需要分行的场景按行分别拉框即可；
- 工作台将来的"对选中区域批量重检测"可直接复用 `ui/region_redetect.py`
  （它不吃 QRectF、不 import Qt widget，只吃 `(page_key, rect)`）；
- **倾斜框在修复环节**：`_blktrans_pipeline` 的修复裁剪用 `enlarge_window(blk.xyxy)`
  （外接矩形），对斜框会偏大——正确性不受影响，只是多算一点；要优化需单独实测；
- 掩码的落盘与手工涂抹/管线覆盖是并集关系，撤销不回退它（见 §4.5）。
