# 模型文件管理 设计方案

> 状态：已完结归档（2026-09-20）——本篇为压缩存档，只留结论与指针；实施过程见 git 历史。
>
> 分层测试流程见 `docs/技术实现/模型文件管理_测试流程.md`（活文档）；首个客户 `paddleocr_vl_manga`
> 的模型细节见 `docs/技术实现/paddle-ocr-for-manga_接入调研_存档.md`；选型文案（哪个模型适合谁）
> 见 `docs/技术实现/模型说明卡片_规划.md`。

## 1. 目标与范围

**在范围内**：四个管线阶段全部**带本地权重**的模块——获取（后台下载 + 手工通道）、总览（装没装、多大、在哪）、释放（删除）。首个用例 `paddleocr_vl_manga`。

**不在范围内**：

- LLM Profile：无本地权重，`ui/llm_profile_cards.py` 已有自己的管理页。
- pip 依赖包的卸载：只谈权重文件。（安装仍复用同一条后台任务，见 §5。）
- 选型说明文案：`docs/技术实现/模型说明卡片_规划.md` 的范围。

机制要盖住的三处缺口：**没有删除出口**（权重装进 `data/models/` 后应用内无释放途径，对无代码基础用户等于「装了就只能留着」）；**没有总览**（只能靠模块下拉的琥珀色猜缺没缺）；**下载被模态框绑住**（安装窗下载期间锁住整个界面，且「Later」会取消模块切换）。

## 2. 复用的既有机制（不重造）

- **模块侧声明**：`modules/base.py::BaseModule` 的 `download_file_list`（下载清单，纯数据，模块自带）；加载期自动下载在 `modules/base.py::_ensure_model_files` 内**同步**执行（按 §5.3 改造）。
- **缺文件检查与提示**：`modules/__init__.py::GET_MISSING_MODEL_FILES`（只读注册表元数据，不导入模块体）；选择器警示色 + tooltip 用 `ui/misc.py::mark_module_selector_status` 与 `ui/misc.py::MISSING_MODEL_ITEM_COLOR`；运行前拦截在 `ui/mainwindow.py` 的 `run_imgtrans` 前置检查（Run Anyway / Cancel）。
- **下载通路与外围**：`utils/download_util.py::download_url_to_file` 内建 `tqdm`（写 stderr）；镜像改写 `utils/mirror.py::maybe_mirror_url` / `utils/mirror.py::patch_hf_env` 由下载器调用、模块侧无需处理，镜像配置界面 `ui/network_settings_dialog.py::NetworkSettingsDialog` 一键含 `hf-mirror.com`；日志 `utils/logger.py` 双写 console 与 `logs/*.log`。

## 3. 设计原则（硬约束）

1. **白名单驱动**：删除对象的唯一来源是模块自己声明的落盘路径。绝不接受运行时拼出来的任意路径，绝不「按目录盲删」。
2. **不碰 git 跟踪的文件**：`data/models/` 下所有权重都被 `.gitignore` 覆盖（`data/models/*`、`*.pt`、`*.ckpt`、`*.onnx`），但 `data/models/ppocrv6_onnx/ppocrv6_dict_proper.txt` 是白名单跟踪的字典文件——删除逻辑必须显式避开它。
3. **下载不打断人**：下载是后台事，进度归终端；只有「用不了」才打断用户。
4. **新模块零改动接入**：新增带权重的模块只改模块文件自身的声明，管理界面代码不动。
5. **不引入第二套下载器**：继续走 `utils/download_util.py::download_and_check_files` 一条路。

## 4. 数据源

### 4.1 `download_file_list` 是惰性 AST 扫描读取的

模块的 `download_file_list` 由 `utils/lazy_registry.py` **惰性 AST 扫描**读取，扫描期不导入模块体，因此**字符串必须是字面量**，不能写 `osp.join`、不能用变量或 f-string 拼。`modules/ocr/ocr_onnx.py::PaddleOCRv6ONNX` 的注释已经记下这条。

推论：**`save_dir` 字段不能用**。`utils/download_util.py::download_and_check_files` 虽然支持 `save_dir`，但两个消费方——`modules/__init__.py::GET_MISSING_MODEL_FILES` 与 `ui/module_manager.py::_ensure_module_deps`——都只读 `save_files`，回落到 `files`，然后相对 `utils/shared.py::PROGRAM_PATH` 拼路径。若只给 `save_dir` + 裸文件名，两处检查都会把裸文件名当成根目录下的路径去找，**全部误报缺失**。落盘路径必须逐条写成完整字面量 `save_files`。

### 4.2 下载清单位：一条条目 + 多文件

`utils/download_util.py::download_and_check_files` 的 `files` / `save_files` 接受等长列表。配合 `concatenate_url_filename: 1`（`url + file`），正好对上 HuggingFace 的 resolve 形态：

```python
download_file_list = [{
    "url": "https://huggingface.co/<repo>/resolve/main/",
    "concatenate_url_filename": 1,
    "files": ["config.json", "model.safetensors"],
    "save_files": ["data/models/<pkg>/config.json",
                   "data/models/<pkg>/model.safetensors"],
}]
```

`utils/mirror.py::maybe_mirror_url` 会把前缀 `https://huggingface.co` 换成本地配置的 `hf_endpoint`，镜像无需在模块侧处理。

### 4.3 包描述 `model_package`（新增）

`download_file_list` 只回答「从哪下、落到哪」，无法回答「这个模块占多大、根目录在哪」。而且**不能从落盘路径反推包目录**：单文件模块（`ysgyolo` 是 `data/models/ysgyolo_yolo26_2.0.pt`、LaMa 是 `data/models/lama_large_512px.ckpt`）反推出的父目录是 `data/models/`——那是全部模型的家，按它算体积、按它删都出事。

因此新增可选类属性 `model_package`（已落地于 `modules/base.py::BaseModule`，惰性扫描字段名同名），只描述包边界，三个字段：`name`＝界面显示名（如 `PaddleOCR-VL-For-Manga`；未声明回落到注册名）；`dir`＝包根目录（相对程序根，用于算体积、打开目录、推导包名；未声明＝**文件型包**，只按声明的 `save_files` 逐个处理，不涉及目录）；`size_hint`＝预期体积（如 `"1.9 GB"`，用于「要下多大」的提示；未声明则不提示）。

**新增带权重的模块必须随附 `download_file_list` 落盘路径 + `model_package` 包描述，否则缺文件检查与体积展示全部失效。** 删除动作**永远以 `save_files` 白名单为准**，`dir` 只用于展示与「打开目录」——即使用户往包目录里丢了自己的文件也不会被删。**只给真正成包的模块声明**：`ysgyolo` 与 `lama_large_512px` 是文件型包（落盘文件就在 `data/models/` 下），**刻意不声明**——它们没有能安全当作「包」的目录。

## 5. 获取：后台下载（行为定稿）

### 5.1 定稿的行为

1. **触发点只有两个**：① 用户在底部栏 / 配置面板 / 运行对话框**选择**某个模块；② 设置页 Models →「模型文件」节点**下载**。
2. 触发后**后台线程立即开始**：不弹确认、不弹进度窗、不阻断任何交互，用户可以继续编辑、翻页、翻译、改设置。**唯一的例外**是命中「本机没有 GPU」硬闸门（§5.5）：必须弹窗说明利害并拒绝，因为放它下完也用不了，还白占 1.9GB。
3. **进度与结果只进终端**（外加 `logs/*.log`）：`utils/logger.py` 的 `LOGGER.info` 同时写 console 与文件，`utils/download_util.py::download_url_to_file` 的 `tqdm` 进度条写 stderr。两者都不需要新做。
4. **未装好就使用**（运行管线 / 加载模型）→ 弹窗提示，指引到 Models →「模型文件」。这是唯一的模态打断，且只针对「用不了」。
5. **下载中可在 Models 页取消**。1.9GB 的下载应当可撤回。取消粒度是**逐块检查**（`utils/download_util.py::download_url_to_file` 每读完一个数据块问一次），大单文件也能秒级停下。取消后：**已下完的文件保留**（下次 `utils/download_util.py::check_local_file` 直接跳过），**正在下的那个文件整份丢弃**——下载走临时文件、完成才落盘，不会留半截文件骗过后续校验。

### 5.2 后台任务层：`ui/model_downloads.py`

- 原先嵌在 `ui/module_manager.py::_ensure_module_deps` 函数体里的安装 worker 提升为模块级公开的 `ModelDownloadTask`，作为两个入口共用的执行器；单例注册表 `ui/model_downloads.py::ModelDownloadRegistry` 持 `modules/__init__.py::GET_MODULE_REQUIREMENTS` 取到的需求，负责防重复触发、供 Models 页查状态与取消、失败时告知一次。
- **注册表必须建在主线程**：`ModuleManager.parent()` 取到的是 `None`（创建时没传 parent），后台任务生命周期不能挂在 widget 上，只能由注册表持有。
- `ui/module_manager.py::_ensure_module_deps` 改为「启动即返回」：签名从 `(module_cls, parent_widget)` 改成 `(module_type, key)`，发现缺依赖或缺模型 → 交给任务层起后台任务 → **立即返回 `True`**，模块照常切换。调用方原有的「回滚选择器」分支随之删掉（不再有 Later）。
- **失败文案资产保留**：原先那套引导（HF 无镜像 → 去 Mirror Config 设 `hf-mirror.com`、pip 失败看日志、网络受限提示）是踩过坑写下的，改为任务失败时 `ui/model_downloads.py::format_failure_message` **弹一次简短告知**，不随模态窗一起删掉。

### 5.3 加载期不再下载（新增声明）

`modules/base.py::BaseModule` 的 `_ensure_model_files` 在 `load_model` 内**同步**调用 `download_and_check_files`。用户若绕开「选模型」直接跑管线，1.9GB 会在主线程同步下载并冻住界面——与 §5.1 第 2 条直接冲突。

新增类属性 `background_download_only = True`（缺省 False，现有模块行为不变）。置 True 的模块，加载期只**检查**不下：文件齐备 → 照常加载；文件缺失 → 抛 `modules/base.py::MissingModelFilesError`（只带结构化信息：模块名 + 缺失文件），由上层按 §5.4 弹窗；**不要放任 `from_pretrained` 抛底层路径错误**。

异常只携带数据、文案在 UI 侧组（`ui/model_downloads.py::missing_model_files_hint`）——`modules/` 里不写中文，i18n 硬编码检查会红。**接住它时注意顺序**：`MissingModelFilesError` 是 `RuntimeError` 的子类，捕获顺序写反会掉进 `ui/module_manager.py::ModuleThread` 里那个「只记 `last_error`、不弹窗」的分支，变成一声不吭。

`paddleocr_vl_manga` 置 True。`ysgyolo` 15MB、LaMa 195MB 这类小模型不必声明，加载期同步补下反而体验更顺。

### 5.4 「用不了」的弹窗

两处：

- **运行管线前**：`ui/mainwindow.py` 的 `run_imgtrans` 前置检查已有此弹窗，只需把文案改为明确指路（Models → 模型文件 → 下载）。
- **加载模型时**：按 §5.3 由加载异常触发，文案同上。**该模块要求 GPU 而本机没有时换文案**：`ui/model_downloads.py::missing_model_files_hint` 接 `requires_gpu` 参数（`MissingModelFilesError` 上带同名属性），改说「这机器上没有 GPU」——此时指路去设置页下载是死路，下载入口本身就会拒绝（§5.5）。

### 5.5 GPU 硬闸门（2026-09-20 定）

**要解决的问题**：CPU 分发包里，用户在「模型文件」页点 `PaddleOCR-VL-For-Manga` 的下载、或在选型界面选中它，都会真的去拉 1.9GB 权重 + 128MB `transformers`；而生成式模型在 CPU 上逐块自回归解码没有实用价值（`_resolve_device` 里那句 "impractically slow on CPU" 警告就是这件事）。用户拍板的策略：**CPU 环境弹窗说明利害并拒绝下载，只在 GPU 环境放行**。

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 声明 | `modules/base.py::requires_gpu`（贯通 `utils/registry.py::ModuleSpec`、`utils/lazy_registry.py::LAZY_CLASS_ATTRS`、`modules/__init__.py::GET_MODULE_REQUIREMENTS` 的 `requires_gpu` 字段） | 模块自己说「我要求加速设备」 |
| 判据 | `modules/base.py::accelerator_available` | `DEFAULT_DEVICE != "cpu"`——导入期已按 torch 实际可用性算过，`BALLOONTRANS_CPU_ONLY=1` 也返回 False。**刻意不用 `torch.cuda.is_available()`**：判据回答的是「跑得动吗」，xpu / mps / directml 同样跑得动 |
| 硬闸门 | `ui/model_downloads.py::ModelDownloadRegistry` 的 `start` | 命中即返回 False，**pip 依赖与权重文件都不碰**；日志记一条（含 `install_cuda.bat` 指引） |

弹窗与徽章：

- 文案与判据同处一地：`ui/model_downloads.py::gpu_required_message` / `ui/model_downloads.py::gpu_requirement_block`（后者是 UI 调用的唯一入口，返回 `""` ＝放行）。文案三段短句（**措辞由用户 2026-09-20 定稿，改动前先问**）：结论（需要 GPU、本次下载已拒绝）、原因（对性能需求高，CPU 上时间开销远大于模型能力）、出路（有支持的 N 卡就跑 `install_cuda.bat` 换 CUDA 版 torch，只有 CPU 就用内置的其他模型）。文字按**普通用户**口径写，不出现 token／自回归／VLM 这类术语；第二段**只说不提供下载**，与闸门的实际范围对齐。
- 两个入口各按自己的既有惯例弹同一个文案：「模型文件」页的下载钮经 `utils/message.py::create_info_dialog`（与下载失败告知同一条通路，`btn_type=Ok`）；`ui/module_manager.py::_ensure_module_deps` 同样经 `create_info_dialog` 弹一次，**模块照常切换**（不回滚选择器）。注意 `_ensure_module_deps` 平时的定稿是「不弹窗」（§5.1 第 2 条），GPU 这条是有意加的例外。
- 「模型文件」页的徽章换成 `需要 GPU`（`ui/model_files_panel.py::_badge_of` 的 `_gpu_blocked` 分支），而不是「缺失 15」——否则用户会一直点下载。行仍可勾选、按钮仍可点，点下去就是那段说明（若把按钮置灰，用户就没有任何解释可看）。

**没做、也不打算做的事**：不管「运行」只管道「下载」。用户把权重从别处拷进来（或已装好 transformers）后仍可选中该模块并跑——`_resolve_device` 会警告并退回 CPU，慢是用户自己的选择；手工通道（§6）本来就该保持畅通。**2026-09-20 用户拍板：只拦下载作为提示就够了，不刻意妨碍运行**，故文案与实现同口径（都只说下载），不引入运行侧硬拦。

## 6. 获取：手工通道

面向国内网络实情（HF 直连不稳），后台下载失败后必须能手工补齐。三样都挂在 Models 页的「模型文件」节：

1. **打开模型目录**：`QDesktopServices.openUrl` 打开包目录，不存在则先创建并打开父目录。
2. **期望文件清单 + 缺失项**：直接复用 `modules/__init__.py::GET_MISSING_MODEL_FILES` 的返回值，让用户能核对「差哪几个」。
3. **下载来源指引**：给出 HF 镜像仓库地址；网盘链接维护在发布页说明与本文档，**不在代码里硬编码**（链接会漂移，硬编码等于埋雷）。

## 7. 释放：删除

### 7.1 安全边界（硬约束）

1. 只删**该模块 `download_file_list` 声明过的 `save_files`**，逐条 `osp.exists` 后再删。
2. 跳过任何被 git 跟踪的文件（当前只有 `data/models/ppocrv6_onnx/ppocrv6_dict_proper.txt`）。运行时不宜调 git，用「白名单 + 排除字典文件名」实现。
3. 删除前若该模块模型已加载，先走 `modules/base.py::BaseModule` 的 `unload_model`；若该模块正在后台下载，先取消任务。
4. 删除前二次确认弹窗：列出待删文件的落点与**总体积**，并说明「可从回收站还原」。

### 7.2 回收站实现

用 `win32com.shell.shell.SHFileOperation`，标志 `FO_DELETE | FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT`（`FOF_ALLOWUNDO` 即送回收站）。已核实：`pywin32` 已在 `requirements.txt` 中（win32 平台），**零新增依赖**；本机实测 `win32com.shell` 可导入，`FOF_ALLOWUNDO = 0x40`；`ctypes` 直调 `shell32.SHFileOperationW` 可作为无 pywin32 环境的备选。

**成功判据不看返回码**（2026-09-20 实测）：同一批文件在不同标志位下给出三种码，而文件都真的进了回收站——无标志返回 `0`；仅 `FOF_ALLOWUNDO` 返回 `1223` 且 `fAnyOperationsAborted` 竟为 **True**；再加 `FOF_SILENT` 或 `FOF_NOERRORUI` 都返回 `2`。明细表见 `docs/技术实现/模型文件管理_测试流程.md`。

故 `utils/model_files.py::delete_paths` 一律以**调用后 `osp.exists`** 判定成败，返回码只作诊断记日志，`fAnyOperationsAborted` 也不采信。若 Shell 调用整个抛异常（无 pywin32 且 ctypes 也不可用），**不偷偷退化为永久删除**——确认框里承诺过可还原，此时全部记失败交界面告知，用户可「打开目录」自己处理。非 Windows 平台不做回收站（本项目实际只发 Windows），退化为直接删除并在确认框里写明不可还原（该分支由 `utils/model_files.py::trash_available` 在弹确认框之前判定，所以文案与实际行为一致）。

### 7.3 删除后的刷新联动

删除会改变「缺文件」状态，必须刷新两处选择器的警示色：底部栏四个选择器（`ui/mainwindow.py` 中批量调用 `ui/misc.py::mark_module_selector_status` 的那段）与运行对话框（`ui/run_pipeline_dialog.py` 中的同名调用）。

## 8. 界面：Models 页新增「模型文件」节

落点：`ui/configpanel.py` 的 Models 页，排在现有 `Model Loading`、`Management` 两节之后。控件在 `ui/model_files_panel.py::ModelFilesSection`（`ui/configpanel.py` 只实例化它并接线，免得把两千多行的设置面板再撑大）；节标题由分节卡给——`ui/configpanel.py::_section_body` 开一张 `Model Files` 卡把整个 section 包住；按钮统一 `objectName="ConfigButton"`（主操作「下载」另设 `ModelFilesPrimaryButton` 加粗）。`ui/configpanel.py::ConfigPanel` 新增两个信号做解耦：`model_unload_requested`（删除前卸载该阶段，接线在 `ui/module_manager.py::ModuleManager`）与 `model_files_changed`（主窗据此重刷选择器警示色）。

**列表形态复用工作台那张自绘行列表**（`ui/custom_widget/row_table.py::RowTable` 的卡片模式），而不是「一行标签 + 一排按钮」的表格草图：一行一张圆角卡，主文＝模型显示名（包描述的名字，回落到注册名），次行＝`阶段 · 注册名 · N 个文件 · 体积`，右侧徽章＝状态。动作按钮统一放列表**下方**，对**勾选集合**生效——与工作台「勾选＝本次要处理的条目」同一套交互，行内不必挤四个按钮。底部状态条给「总数 · 勾选数 · 占盘」；表格高度按行数自适应（最多 5 行，再多表内滚动）。

**徽章**（delegate 取主题色）：已就绪 `muted`（声明文件齐备且依赖已装）／缺 N 项 `warning`（`modules/__init__.py::GET_MISSING_MODEL_FILES` 报缺文件）／缺依赖 `warning`（缺 `requires_packages`）／下载中或 N% `accent`（注册表里该模块有任务在跑）。**动作**（均对勾选集合生效）：下载＝勾选项中有缺文件或缺依赖的（§5.2 的任务层）／取消＝勾选项中有正在下载的（否则整个按钮隐藏）／删除＝勾选项中有文件在盘上（§7）／打开目录＝恰好勾选一项（§6）。

复用该控件时补掉它两处不足（改动都在 `ui/custom_widget/row_table.py`，对工作台无行为变化）：卡片模式没有表头、`set_header_labels` 不会被调用，故列宽规则要在构造时先套一次（否则单列停在默认宽度、卡片被压成窄条——2026-09-20 实测踩到）；徽章的让位宽度原先写死 56px，长徽章会压到主文上，改为按实际文字度量。另新增 `ui/custom_widget/row_table.py::update_row`，供下载进度这类高频刷新就地更新单行——`set_rows` 会重置模型、清选中、把滚动位置弹回顶部。

文案一律 `self.tr()`，且**必须是单个字符串字面量**（`scripts/i18n_common.py::extract_tr_calls` 不认隐式拼接），新增条目同步 `translate/zh_CN.ts` 并跑 `scripts/i18n_check.py`。

## 9. 首个用例：paddleocr_vl_manga

**仓库实况（2026-09-20 拉 HF API 核对）**：`jzhang533/PaddleOCR-VL-For-Manga` 共 **22 个文件 / 1.93GB**，`gated=false`（无需授权），Apache-2.0，参数量 0.96B（BF16，权重单文件 `model.safetensors` 约 1.79GiB）。

**必需 15 个**（排除 `.gitattributes`、`README.md`、5 张 `examples/*.png`）：`added_tokens.json`、`chat_template.jinja`、`config.json`、`configuration_paddleocr_vl.py`、`generation_config.json`、`image_processing.py`、`model.safetensors`、`modeling_paddleocr_vl.py`、`preprocessor_config.json`、`processing_paddleocr_vl.py`、`processor_config.json`、`special_tokens_map.json`、`tokenizer.json`、`tokenizer.model`、`tokenizer_config.json`。其中 4 个 `.py` 是远端代码（`trust_remote_code=True` 时会被执行），提示文案里要讲清来源。

**接入参数**

| 项 | 取值 |
| --- | --- |
| 注册名 | `paddleocr_vl_manga` |
| 文件 | `modules/ocr/ocr_vl_manga.py`（按 `ocr_` 前缀命名规范） |
| 基类 | `modules/ocr/base.py::OCRBase`，形态参照 `modules/ocr/ocr_onnx.py::PaddleOCRv6ONNX` |
| 包目录 | `data/models/paddleocr_vl_manga/` |
| 依赖 | `requires_packages = ["transformers>=4.57.1,<5"]`（按需装，不进 `requirements.txt`） |
| 下载策略 | `background_download_only = True`（§5.3） |
| 设备 | GPU-only，`device` 缺省即 `cuda`；另声明 `requires_gpu = True`（§5.5 的硬闸门） |
| 包描述 | `model_package = {"name": "PaddleOCR-VL-For-Manga", "dir": "...", "size_hint": "1.9 GB"}` |

实现上有三条与调研文档不同的地方，都是落地时才定的（推理契约、`use_cache` 陷阱、整块裁剪与批量细节见 `docs/技术实现/paddle-ocr-for-manga_接入调研_存档.md` 第 2、4 节，本文不重复）：

1. **裁剪不用 `onnxocr`**。调研 §4 建议用 `onnxocr.utils.get_rotate_crop_image` 做透视校正，但本模块只声明 `transformers`——引入 `onnxocr` 会多一个未声明的依赖。改为取 `utils/block_geometry.py::poly_bands`（块内 `lines` 顶点的轴对齐外接范围）后直接切片：Manga109-s 的训练 crop 本就是轴对齐外接框，切片无重采样，还省掉了网点插值失真。
2. **批量做成参数而非默认**。`batch_size` 缺省 1（逐块），批量左 padding 与 mrope 的兼容性未验证，错了是静默出错，不能当默认。
3. **不挂置信度标签**。生成式模型没有可信分数，`utils/block_tags.py::apply_ocr_confidence_tag` 在本模块下不启用（调研 §4 已预判）。

**环境实况（与调研文档不符，已核实）**：本机 torch 为 `2.13.0+cu132`、`torch.cuda.is_available()` 为真、GPU 为 RTX 5070 Ti Laptop（11.9GB，CC 12.0，原生支持 bf16）。调研文档「本机无 CUDA、torch 为 cpu 版」的记载已过时，其部署清单第 1 步无需执行。

## 10. 已定案的小问题

1. **加载期同步下载** → 新增 `background_download_only` 声明，大模型只走后台（§5.3）。不在加载期下载，不冻界面。

4. **scripts/download_models.bat 已与当前模型集合脱节**（内容还是 `ctd` / `mit48px_ctc` / `aot` 三个已删除模块）→ **删除**（2026-09-20 执行）。权重获取已收敛到应用内按需后台下载，该脚本没有剩余用途；它被 `.gitignore` 覆盖、不在版本控制内，删除前在 `tmp/backup_download_models.bat` 留了一份备份。同步撤掉了 `scripts/README.md` 的登记行与 `docs/项目概述.md` 目录树里的提及。`scripts/download_models.sh` **暂不动**——它的模型下载段同样是上游遗留，但还含 PyPatchMatch 编译步骤（`modules/inpaint/patch_match.py` 依赖），已在 README 里注明其下载段已过时、权重请走应用内入口。
