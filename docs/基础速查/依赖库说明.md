# 依赖库（ballontrans_pylibs_win）说明

## 概述

`ballontrans_pylibs_win/` 是一个自包含的嵌入式 Python 环境，预装了所有项目运行时依赖。位于项目根目录，`launch.py` 和 `launch.bat` 自动识别并使用它。

这个目录有两种出现方式，按发行渠道二选一：

| 渠道 | 这个目录里有什么 | 谁装依赖 |
|---|---|---|
| **引导包**（`scripts/build_win_minimal.ps1` 产物，约 32 MB） | 裸的嵌入式 Python + pip + `uv.exe` | 首启动由 `utils/core_requirements.py::ensure_core_requirements` 装核心依赖（约 520 MB），模型推理包在选中模块时由 `modules/base.py::ensure_dependencies` 按需装 |
| **预装一体包**（网盘兜底的完整包） | 下面「手动安装步骤」装好的全套（约 1.7 GB） | 无需安装，解压即用 |

两条路都用同一个 `launch.bat`，运行时逻辑一致（首启动探测缺包 → 补装 → 重启），区别只在"依赖是否已经躺在包里"。引导包是给有可用网络的用户的省流量选项；没有网络或不想折腾的用户仍走预装一体包。

| 项目 | 值 |
|---|---|
| **Python 版本** | 3.12.4（embedded amd64） |
| **pip 版本** | 26.1.2 |
| **总大小** | ~1.6 GB（预装包；引导包仅约 32 MB） |
| **依赖来源** | `requirements.txt`（核心依赖）+ 下文「安装模型推理包」四批（torch / ultralytics / onnxruntime / onnxocr） |

## 体积演变（历史）

旧环境（Python 3.13，~1.0 GB）**不含 torch**；现环境 ~1.6 GB 的增量几乎全部来自首次引入 torch CPU（529 MB，wheel 自带全套 CPU 算子）+ ultralytics（9 MB）及其传递依赖（sympy 74 MB、matplotlib 33 MB 等）。后续已裁掉 ultralytics 传递来的非必需包 polars（~176 MB）；旧版依赖目录（Python 3.13, ~1.1 GB）已删除。

`PyQt6-Qt6` 的 Qt6 C++ DLL 不单独建目录，直接放在 `PyQt6/` 目录下（`pyqt6_qt6-6.11.1.dist-info` 只是元数据），`PyQt6/` 合计 215 MB 已含 Qt6 运行时。

## 手动安装步骤

重建该环境时按以下步骤手动搭建（**预装一体包**就是按这套步骤做出来的；引导包不走这里，它只放裸 Python + pip + uv，见 `scripts/build_win_minimal.ps1`）：

### 前置条件

- Windows x64
- 网络能访问 `python.org` 和 `pypi.org`（或国内镜像）
- 项目已 clone 到本地

### 操作步骤

**1. 下载 Python 3.12.4 embeddable**

```
https://www.python.org/ftp/python/3.12.4/python-3.12.4-embed-amd64.zip
```

**2. 解压到项目根目录，重命名为 `ballontrans_pylibs_win/`**

确保 `ballontrans_pylibs_win\python.exe` 存在。

**3. 启用 site-packages**

编辑 `ballontrans_pylibs_win\python312._pth`，把 `#import site` 改为 `import site`（去掉注释）。不改的话 pip 装的包无法导入。

**4. 安装 pip**

```cmd
cd 项目根目录
.\ballontrans_pylibs_win\python.exe -c "import urllib.request; exec(urllib.request.urlopen('https://bootstrap.pypa.io/get-pip.py').read())"
```

如果 SSL 报错，手动下载 `get-pip.py` 到本地后执行：

```cmd
.\ballontrans_pylibs_win\python.exe get-pip.py --no-warn-script-location
```

**5. 安装核心依赖**

```cmd
.\ballontrans_pylibs_win\python.exe -m pip install -r requirements.txt --prefer-binary --no-warn-script-location
```

**6. 安装模型推理包（发行版必备，四批都要装）**

`ultralytics` 不在 `requirements.txt` 里（它是按需依赖，源码用户由应用在加载 YOLO 检测器时自动补装），但打包分发时必须预先装好，否则用户拿到的是残包。

```cmd
rem 第一批：PyTorch CPU（~529 MB，大文件注意网络超时）
.\ballontrans_pylibs_win\python.exe -m pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu --prefer-binary --no-warn-script-location

rem 第二批：YOLO 检测
.\ballontrans_pylibs_win\python.exe -m pip install ultralytics --prefer-binary --no-warn-script-location

rem 第三批：ONNX OCR
.\ballontrans_pylibs_win\python.exe -m pip install onnxruntime --prefer-binary --no-warn-script-location
.\ballontrans_pylibs_win\python.exe -m pip install onnxocr --no-deps --no-warn-script-location

rem 第四批：效果渲染加速（~147 MB；发行包已预装，缺失时渐变/网格变换退回纯 NumPy）
.\ballontrans_pylibs_win\python.exe -m pip install numba --prefer-binary --no-warn-script-location
```

> `onnxocr` 声明了 `numpy<2.0` 约束，与当前 numpy 2.x 冲突，必须用 `--no-deps` 跳过。

**刻意不装 `transformers`（2026-09-20 定）。** 它是 `modules/ocr/ocr_vl_manga.py` 唯一的用途，而那个模块是「质量优先、GPU 强烈建议」的生成式 VLM：CPU 上逐块自回归解码没有实用价值，而 CPU 发行包面向的正是没有独显、跑不了 CUDA 的用户——装进去只是白占 ~128 MB（`transformers` 本体 113 MB，自带全部模型架构定义）。有 GPU 的用户换装 CUDA 版 torch 后，在应用里选中该 OCR 模块即由 `modules/base.py::ensure_dependencies` 自动补装 `>=4.57.1,<5`（区间收在 `modules/ocr/ocr_vl_manga.py::requires_packages`），不需要人工干预；不需要 sentencepiece。该模块同时声明了 `requires_gpu = True`，所以**没有 GPU 的机器上「模型文件」页点下载会被拒绝并弹窗说明**（不会拉 1.9GB 权重、也不会装 transformers），而不是下完才发现跑不动——闸门口径见 `docs/技术实现/模型文件管理_设计方案_存档.md` §5.5。

**7. 验证**

```cmd
rem 核心依赖
.\ballontrans_pylibs_win\python.exe -c "import sys; print(sys.version); import torch; import cv2; import PyQt6; print('All core deps OK')"
```

VL OCR 那条链路**不在 CPU 包的验收范围**（它按上面的决定不装 transformers）。若做的是 GPU 包、或想单独确认该模块能加载，再跑这一条（需已下载 `data/models/paddleocr_vl_manga`；`transformers` 是在 `_load_model` 里才导入的，模块级 import 探针看不见它，缺包只在加载模型那一刻暴露）：

```cmd
.\ballontrans_pylibs_win\python.exe -c "import os,sys; sys.path.insert(0,os.getcwd()); from modules.ocr.ocr_vl_manga import PaddleOCRVLManga; m=PaddleOCRVLManga(device='cpu'); m.load_model(); print('VL OCR deps OK'); m.unload_model()"
```

> **这条命令会自己装东西**：`load_model()` 先跑 `modules/base.py::ensure_dependencies`，发现缺 `transformers` 就联网补装（连带的 tokenizers / safetensors / huggingface_hub / regex 一起，~128 MB）。在刻意不装 transformers 的 CPU 包上跑它，会把这批包又装回去——想要干净的 CPU 包就别跑，或跑完再 `pip uninstall transformers`。

`scripts/probes/ocr_vl_manga_accept.py` 是更完整的端到端验收，但它要读 `torch.cuda.*` 的显存读数，**只能在 CUDA 版依赖包里跑**。

## 多机同步说明

给另一台电脑同步时：

**方法 A：直接拷贝 `ballontrans_pylibs_win/` 目录（推荐）**

把本机完整的 `ballontrans_pylibs_win/` 复制到目标机的项目根目录即可。该目录是自包含的，不依赖注册表或系统路径。注意：
- 确保目标机安装了 [VC++ Redistributable 2015-2022](https://aka.ms/vs/17/release/vc_redist.x64.exe)（embedded Python 依赖它）
- 如果目标机有 Windows 标记为「来自另一台计算机」导致 exe 被阻止，右键 `ballontrans_pylibs_win\python.exe` → 属性 → 「解除锁定」

**方法 B：重建（目标机网络良好时）**

在目标机上按上面「手动安装步骤」重建 `ballontrans_pylibs_win/`。第 6 步的四批必须全装，只装核心依赖会得到一个没有 YOLO 检测、没有 ONNX OCR 的残环境（`transformers` 按上面第 6 步的说明刻意不装）。

## 与上游共用同一依赖库

同时使用上游 BallonsTranslator 与本 fork 时，可以让一份 `ballontrans_pylibs_win/` 服务两个项目：把上游的 `ballontrans_pylibs_win/` 目录（复制或目录联接/符号链接均可）放到本 fork 根目录，照常 `launch.bat` 启动。

fork 启动时的核心依赖探测（`launch.py` 调 `utils/core_requirements.py::ensure_core_requirements`）发现缺包会自动增量补装，且补装带**只增不升**保障：安装前对环境里已装的发行版做 `名称==版本` 快照，作为 pip/uv 的 `-c` 约束传入（见 `utils/package_installer.py::build_install_command`），任何会升级既有包的解析直接失败、快照文件留盘交人工决策，绝不静默改动上游正在用的版本。

两边依赖集的差异很小，共享环境下的增量通常只有：

- **fork 独有**：`openai`、`pydantic`、`httpx[socks,brotli]`、`fonttools`、`termcolor`（翻译 agent 与字体扫描链路）及其少量传递依赖；其余 fork 声明上游 `requirements.txt` 已覆盖或已装版本满足。
- **上游独有、fork 不需要**：`python-docx`、`docx2txt`、`piexif`、`ordered-set`、`brotlicffi`——fork 代码无引用，装了也不碍事，不必卸。
- **`numba`**：两边都受益（fork 的渐变/网格效果加速内核），上游 requirements 自带；fork 独立安装时可走 `pyproject.toml` 的 `acc` extra，缺失时自动退回纯 NumPy。
- **`transformers`（`paddleocr_vl_manga` 用）**：fork 的 CPU 发行包刻意不带它（理由见第 6 步），从上游环境借过来时同理——上游有就直接用（版本需落在 `>=4.57.1,<5`），没有也不补：那是 GPU 用户选中该 OCR 模块时才由 `modules/base.py::ensure_dependencies` 自动装的，共享环境里不会顶掉上游的其它包。

版本约束上两边已无冲突：fork 曾因 pillow-jxl-plugin 兼容性钉 `pillow<11`，实测上游环境 pillow 12.2.0 + pillow-jxl-plugin 1.3.7 的 JXL 编解码正常，该钉子已解除。

若把依赖库放在 fork 根目录之外，也可以不复制：用 `mklink /J ballontrans_pylibs_win <上游路径>` 建目录联接，两个项目指向同一份物理目录，补装发生在同一处、对两边同时生效。
