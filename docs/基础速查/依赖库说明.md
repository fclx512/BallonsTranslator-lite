# 依赖库与 Windows 运行环境

## 普通用户先选完整包

Windows 正式使用优先下载与源码版本、CPU/CUDA 档位匹配的网盘完整包。完整包把
`ballontrans_pylibs_win/`、源码和该发行配置的模型后端放在一起，解压后运行
`launch.bat`；启动器只使用包内 Python，不调用系统 Python、PATH 中的解释器或用户
site-packages。缺少匹配环境时会提示重新取得完整包。离线机器应使用该包，不能指望
首启在线安装。

Windows 源码开发同样建议从对应完整包取得 `ballontrans_pylibs_win/` 并解压到源码根目录，
再运行 `launch.bat`。CPU 与 CUDA 包不是可随意互换的目录；切换档位时使用对应环境包。
启动检查根目录 `runtime_compatibility.json` 的源码兼容声明，并在有发行清单时校验包的
身份和档位。声明约束源码支持范围，包内精确清单记录具体发行环境；静态清单检查不等于
模型推理或整机运行验收。

约 30 MB 的 `BallonsTranslator-lite_win_min.zip` 是维护者/高级用户用的轻量引导包，包含
源码和嵌入式 Python，但不带完整依赖、模型后端或权重。普通启动不会联网安装核心依赖；
只有用户明确同意联网修复时才运行 `launch.bat --repair-deps`。轻量包不适合作为离线或
普通用户的默认安装方式。网盘完整包才是自包含发行路径，轻量包构建说明见
`scripts/README.md`「轻量包构建」。

## 声明文件与发行清单

- `requirements.txt` 与 `pyproject.toml` 声明核心依赖的**版本范围**，不是某次发行环境的
  精确锁定结果。项目元数据中的 `requires-python` 也描述通用源码范围；Windows 配套包
  的 Python 主次版本另由 `runtime_compatibility.json` 标注。
- `runtime_compatibility.json` 是源码兼容契约，声明 schema、环境 family、支持的 Python
  系列和 CPU/CUDA profiles。它不表示当前开发环境已通过发行验收。
- 完整环境包内 `runtime-manifest.json` 记录 `bundle_id`、profile、family、Python 版本、
  实际安装的精确 distributions，以及随包模型文件的 SHA256。它是该包的可复核快照，不能
  单凭“生成成功”推断真实推理已验收。
- 维护者从准备好的发行目录离线核对 CPU/CUDA 环境及模型文件：

  ```cmd
  ballontrans_pylibs_win\python.exe scripts\check_bundle.py --profile cpu
  ballontrans_pylibs_win\python.exe scripts\check_bundle.py --profile cu126 --include-vl
  ballontrans_pylibs_win\python.exe scripts\check_bundle.py --profile cu130 --write-manifest --bundle-id lite-vX.Y.Z-cu130
  ```

  支持档位以 `runtime_compatibility.json` 为准（目前包括 `cpu`、`cu126`、`cu130`、
  `cu132`）。`--write-manifest` 只应对已经准备好的具体发行目录使用；不能拿共享的开发
  环境清单代替发布包快照。检查器会拒绝缺依赖及明显的混装状态。

## 依赖声明

公共依赖版本范围应在 `requirements.txt` 和 `pyproject.toml` 同步维护。当前与上游共同
使用的最低版本为：

| 依赖 | 最低版本 | 用途/维护口径 |
| --- | --- | --- |
| `PyQt6-Qt6` | `>=6.11.1` | Qt 运行库 |
| `PyQt6` | `>=6.11.0` | Python Qt 绑定 |
| `numpy` | `>=1.22` | 数值计算；本仓库图像与模型链路依赖 |
| `requests` | `>=2.32.4` | 网络请求 |
| `tqdm` | `>=4.66.3` | 终端进度显示 |

以下保留本 fork 现有声明的较高下限，和上游范围不完全一致；这里只记录维护选择，不把
它们包装成已证明的单一 API 硬要求：`opencv-python>=4.10.0.84`、`networkx>=3.0`、
`packaging>=23.0`、`pillow>=10.0`。更新这些范围前应先查本 fork 的用法和发行环境，并
验证项目支持的配置，不要为了版本数字整齐而机械降级或追新。

模型后端与大型模型库不属于上述核心依赖范围，应随 CPU/CUDA 完整包按档位搭配。独立
模块的 `requires_packages` 会在相应功能需要时检查依赖；离线用户应预先获取已配好的环境，
不能假设模块首次启用时网络可用。`numba` 仅用于效果渲染加速，仍是可选依赖；缺失时
回退到 NumPy 路径。独立安装加速 extra 可用 `pip install -e ".[acc]"`。

显式在线补装会固定已安装库的版本；若解析需要升级或降级现有库则报错，不自动改变基础
环境。只有 `onnxocr` 这一已登记的依赖声明冲突使用 `--no-deps`，其他失败不会无依赖重试。
GPU ONNX Runtime 的变更交由完整包或 CUDA 维护工具处理，避免从普通安装入口装错档位。

### cu132 候选中保留的依赖声明例外

2026-10-23 的固定候选环境仍有 7 条 `pip check` 错误。以下结论基于包内已安装版本的
元数据和源码，以及该候选的真实图片推理记录；不修改第三方元数据，也不把声明冲突改称通过。

| 报错项 | 已核对的原因与处理边界 |
| --- | --- |
| onnxocr 缺 onnxruntime（1 条） | `onnxocr==2025.5` 使用 `onnxruntime` import；候选由 `onnxruntime-gpu==1.27.0` 提供。CPU 与 GPU distributions 共享文件，不能为满足发行名再并装 CPU 包。CPU 分发应保留 CPU ORT。 |
| onnxocr 缺两种 OpenCV 包（2 条） | 同时声明 headless 和 contrib，而候选只有 `opencv-python==5.0.0.93`。本应用调用的检测/OCR 图片路径涉及的 22 种基础 cv2 API 均存在，未发现 contrib 专属调用；不再混装覆盖同一 cv2 目录的包。 |
| onnxocr 缺 pdf2image、pymupdf（2 条） | 安装包的独立 PDF 转换脚本使用这两项；本应用通过 `modules/textdetector/detector_paddlev6.py` 和 `modules/ocr/ocr_onnx.py` 直接调用图片检测/识别，不导入该 PDF 脚本。本记录不认证第三方库的 PDF 功能。 |
| ultralytics 缺 polars（1 条） | `ultralytics==8.4.86` 的 DataFrame/CSV/JSON 结果导出等路径需要它；`modules/textdetector/detector_ysg.py` 直接读取预测 boxes 和张量，不使用这些导出。图片预测已验收，不代表第三方库全部功能可用。 |
| onnxocr 与 NumPy 上限冲突（1 条） | onnxocr 要求 `numpy<2`，候选为 `numpy==2.5.0`；同时当前 OpenCV 在 Python 3.12 下要求 `numpy>=2`，两者没有共同满足的 NumPy 版本。单独降级无法解决，必须另建候选并重新验收整套组合。当前只保留已验收的应用图片路径。 |

这些例外属于此 cu132 候选，不自动适用于旧 CPU 网盘包。跨电脑更新前先用原包内 Python
核对 Python 3.12、核心依赖范围和 CPU 后端；源码测试更新包不携带依赖或模型。旧包不满足
当前声明时，保留旧环境和原配置，准备独立 CPU 候选后再验收，不能覆盖为 cu132 环境。

## 维护者：检查与 CUDA 环境

`scripts/check_bundle.py` 是发行目录的静态依赖和文件清单检查入口；它验证声明范围与
环境实际安装状态，并可选写入包内精确 manifest。静态检查不覆盖启动、模型加载、显卡
驱动或端到端推理，因此需与发行验收记录配合。

默认清单覆盖 PPOCRv6 检测/OCR、YSG YOLO、YSG+CTD、LaMa 和 PatchMatch（含
`data/libs/` 的原生 DLL）；PaddleOCR-VL 的依赖及权重仅在 `--include-vl` 时计入。
Windows 启动及环境检查通过 `utils/bundled_runtime.py::prepare_bundled_dlls` 优先加载
包内 Qt 目录已有的 MSVC DLL，并保留 DLL 搜索目录句柄；Python 自身运行库仍由解释器
目录提供。发行验收须检查进程实际加载路径，不能仅因开发机装有运行库而判定完整包可用。
复查已有清单时使用相同的 profile 和 `--include-vl` 选择；版本或模型文件偏离快照会报错。
源码更新在覆盖前检查新版本的兼容声明和核心依赖范围；不兼容时保留当前源码，提示换用
匹配完整包。没有兼容声明的旧版源码不通过新版更新入口直接覆盖。

`install_cuda.bat` 默认只读取 `ballontrans_pylibs_win/`，检查 GPU 对应档位并输出方案；
`install_cuda.bat --json` 提供只读机器格式。只有显式传 `--install` 才会联网更改包内
Torch/ONNX Runtime 组件。它不是普通用户的安装向导，不操作系统 Python 或其他 venv。
普通用户应直接取得匹配的 CUDA 完整包。索引、驱动和版本组合的维护记录见
`docs/技术实现/CUDA环境与索引_说明.md`。

## 后续更新原则

不随每次启动或每个上游提交升级依赖。共享库的声明尽量与上游保持一致，但具体发行包
固定到通过验收的一组版本；调整声明不代表立即替换包内库。上游升级只有涉及安全修复、
当前故障、必要功能或新版硬件支持时才优先跟进，其余在准备下一次完整包时集中评估。
Torch/TorchVision/ONNX Runtime/CUDA 和 OCR 模型后端按组合验收，不能单独追最新版。

源码与完整包使用相同 family 时仍须满足实际声明范围；改变 Python ABI、模型后端接口或
已验证的基础组合时应更新兼容 family 并分发新包。为方便用户回退，保留上一版完整包及
对应清单。发布前还需在没有另装 Python/Qt/NumPy 的机器上验证解压启动和模型推理；
CUDA 档仍依赖操作系统中的 NVIDIA 驱动，不依赖本机 CUDA Toolkit 或 Python 环境。

## 维护者：准备完整环境

完整包所用目录来自经过验证的 CPU/CUDA 环境，不能由 `scripts/build_win_minimal.ps1`
生成——该脚本只构建轻量引导包。清单应在确认环境、模型文件和发行档位后生成；不要把
本机开发依赖快照称为发行认证。模型具体文件由各模块的
`modules/ocr/ocr_vl_manga.py`、`utils/model_files.py` 等声明，权重仍统一位于
`data/models/`。

检查 `ballontrans_pylibs_win/` 是否存在及 Python 能否运行：

```cmd
ballontrans_pylibs_win\python.exe -c "import sys; print(sys.version); import PyQt6, numpy, cv2; print('core imports OK')"
```

这条命令只做导入冒烟，不替代 `scripts/check_bundle.py`、应用启动或模型端到端验收。
